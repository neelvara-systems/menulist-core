## Overview

The pricing plans system allows administrators to manage subscription plans and enables customers to subscribe to these plans. The implementation follows a two-part architecture:

1. **Firebase Database**: Stores plan details, features, and UI-related information
2. **Stripe**: Handles payment processing and subscription management

This approach provides flexibility to update plan features and descriptions without changing the payment infrastructure, while maintaining version history for existing subscribers.

The system also implements multi-tenancy support, ensuring that subscription data is properly scoped to specific tenants (tId) and stores (sId) throughout the entire subscription lifecycle.

## Database Implementation

### Data Model

Pricing plans are stored in the Firebase Firestore collection `pricingPlans` with the following structure:

```typescript
export interface PricingPlan {
    id?: string;
    name: string;
    price: number;              // Stored in paise (1 INR = 100 paise)
    periodicity: 'MONTH' | 'YEAR';
    features: string[];
    recommended?: boolean;      // Highlight as recommended plan
    stripeMonthlyPriceId?: string;  // Reference to Stripe price ID for monthly billing
    stripeYearlyPriceId?: string;   // Reference to Stripe price ID for yearly billing
    active: boolean;            // Whether plan is currently offered
    version: number;            // For tracking changes to plans
    createdOn?: any;            // Timestamp
    modifiedOn?: any;           // Timestamp
}
```

### Database Operations

The following operations are supported via the `database/pricingPlans` module:

1. **Get All Plans**: Retrieves all plans regardless of active status
   ```typescript
   const allPlans = await getAllPricingPlans();
   ```

2. **Get Active Plans**: Retrieves only active plans for customer display
   ```typescript
   const activePlans = await getActivePricingPlans();
   ```

3. **Create Plan**: Adds a new pricing plan
   ```typescript
   const newPlan = await addPricingPlan(planData);
   ```

4. **Update Plan**: Updates an existing plan (increments version number)
   ```typescript
   const updatedPlan = await updatePricingPlan(planData);
   ```

5. **Deactivate Plan**: Marks a plan as inactive
   ```typescript
   await deactivatePricingPlan(planId);
   ```

## Stripe Integration

### Setting Up Plans in Stripe

1. Log into the [Stripe Dashboard](https://dashboard.stripe.com/)
2. Navigate to Products > Create Product
3. For each plan, you'll need to:
   - Create a product representing the plan (e.g., "Basic Plan")
   - Create two prices for the product:
     - Monthly price (recurring, billed monthly)
     - Yearly price (recurring, billed yearly)
4. Save the price IDs generated by Stripe (they look like `price_1Abc123Xyz456Def789`)

### Connecting Stripe with Database

After creating prices in Stripe, copy the price IDs into your database records:

```typescript
const planData = {
    name: "Business Plan",
    price: 20000,  // ₹200.00
    periodicity: "MONTH",
    features: ["Feature 1", "Feature 2", "Feature 3"],
    recommended: true,
    stripeMonthlyPriceId: "price_1Abc123Xyz456Def789",
    stripeYearlyPriceId: "price_1Def456Xyz789Abc123",
    active: true,
    version: 1
};

await addPricingPlan(planData);
```

### Stripe Checkout vs Payment Intents

We use Stripe Checkout Sessions for subscription management rather than Payment Intents. Here's why:

#### Stripe Checkout Sessions

```typescript
// API endpoint returns checkout URL
return NextResponse.json({
  url: checkoutSession.url,
}, { status: 200 });

// Client redirects to Stripe hosted checkout
window.location.href = data.url;
```

**Benefits:**
- **Hosted by Stripe**: Uses Stripe's pre-built, professionally designed payment page
- **Optimized for subscriptions**: Specifically designed for handling recurring billing
- **Handles complexity**: Manages payment methods, customer creation, and subscription creation
- **Less development work**: No need to build custom payment forms
- **Webhooks based**: Updates come through webhooks rather than direct client-side events

#### Payment Intents (Alternative Approach)

```typescript
// API endpoint returns client secret
return NextResponse.json({ 
  clientSecret: paymentIntent.client_secret 
}, { status: 200 });

// Client renders custom payment form with Stripe Elements
<Elements stripe={stripePromise} options={{ clientSecret }}>
  <PaymentForm />
</Elements>
```

**Characteristics:**
- **Requires custom UI**: You need to build your own payment form using Stripe Elements
- **Client-side processing**: The payment is processed directly in the browser
- **Single payment focus**: Better suited for one-time payments than subscriptions
- **More control**: Gives you complete control over the payment flow and UI
- **More complex**: Requires handling payment methods, validation, and errors yourself

**Why We Chose Checkout Sessions:** For subscription-based systems, Checkout Sessions provide a more streamlined user experience and simplified development process, while handling all the complexities of recurring billing.

## Implementation Flow

### Creating/Updating Plans

1. **Admin Action**: Admin creates or updates a plan in the admin dashboard
2. **Database Update**: Plan is stored in Firebase with Stripe IDs
3. **Customer Display**: Active plans are displayed to customers

### Subscribing to Plans

1. **Plan Selection**: Customer views and selects a plan
2. **Billing Cycle Choice**: Customer chooses monthly or yearly billing
3. **Checkout Creation**: Application uses the appropriate Stripe price ID (monthly/yearly) to create a Stripe Checkout session
   - Tenant ID (tId) and Store ID (sId) are included in the metadata
   - These IDs are stored in both the session metadata and customer metadata
4. **Redirect to Stripe**: Customer is redirected to Stripe's hosted checkout page
5. **Payment Processing**: Stripe handles the payment method collection, validation, and subscription creation
6. **Return to Application**: After payment, customer is redirected back to the application
7. **Webhook Processing**: Stripe sends webhook events that your application processes to update subscription status
   - Tenant ID and Store ID are extracted from session metadata and customer metadata
   - These IDs are passed to the subscription creation function
8. **Subscription Storage**: Based on webhook data, subscription details are stored in the user's account with tenant and store context

## User Workflow

### Administrator Workflow

1. Admin logs into the platform dashboard
2. Navigates to Settings > Pricing Plans
3. Can view all plans (active and inactive)
4. Can create new plans, edit existing ones, or deactivate plans
5. When creating/editing a plan, admin enters:
   - Plan name
   - Price
   - Features list
   - Stripe price IDs for monthly and yearly billing

### Customer Workflow

1. Customer views the pricing page
2. Sees all active plans with their features and pricing
3. Selects a plan and billing cycle (monthly/yearly)
4. Proceeds to Stripe checkout
5. After successful payment, gains access to the plan features

## Best Practices

1. **Always Create Stripe Prices First**: Create prices in Stripe before adding them to your database
2. **Version Control**: Never delete plans; deactivate them instead to maintain history
3. **Price Storage**: Store prices in paise (smallest currency unit) to avoid floating-point issues
4. **Feature Lists**: Keep feature lists clear and concise
5. **Testing**: Always test the full subscription flow in Stripe test mode before going live
6. **Backup IDs**: Keep a secure record of all Stripe IDs outside of your application
7. **Webhook Security**: Always verify webhook signatures using your webhook secret
8. **Error Handling**: Implement robust error handling for subscription operations
9. **Idempotency**: Handle webhook events idempotently to prevent duplicate processing
10. **User Experience**: Design your plan selection UI to clearly show available billing options
11. **Multi-tenancy Context**: Always include tenant ID (tId) and store ID (sId) in all subscription operations

## Webhook Implementation

Webhooks are a critical part of the subscription system, as they allow Stripe to communicate events back to your application:

1. **Create a Webhook Endpoint**: Implement `/api/webhook` route to receive Stripe events
2. **Configure in Stripe Dashboard**: Add your webhook endpoint URL to the Stripe dashboard
3. **Secure with Signing Secret**: Verify webhook signatures using your Stripe webhook secret
4. **Extract Multi-tenancy Context**: Extract tenant ID (tId) and store ID (sId) from event metadata

   - `checkout.session.completed`: When a customer completes checkout

## Multi-tenancy Support

The subscription management system fully supports multi-tenancy through the use of tenant IDs (tId) and store IDs (sId) throughout the entire subscription lifecycle.

### Subscription Data Model

The Subscription interface includes tenant and store context:

```typescript
export interface Subscription {
  id?: string;
  userId: string;         // ID of the user who created the subscription
  uId: string;           // User ID (potentially different from userId for legacy reasons)
  tId: string;           // Tenant ID for multi-tenancy support
  sId: string;           // Store ID for multi-tenancy support
  customerId: string;    // Stripe customer ID
  status: "active" | "canceled" | "incomplete" | "incomplete_expired" | "past_due" | "trialing" | "unpaid";
  planId: string;        // Plan ID from our database
  planName: string;      // Name of the plan at the time of subscription
  // Other fields...
}
```

### Multi-tenant Flow

1. **Subscription Creation**:
   - When creating a checkout session, tenant ID and store ID are included in the metadata:
   ```typescript
   const checkoutSession = await stripe.checkout.sessions.create({
     // Other checkout parameters
     metadata: {
       userId: session.uId,
       planId: planId,
       planName: planName,
       tId: session.tId,   // Tenant ID from session
       sId: session.sId    // Store ID from session
     },
   });
   ```

2. **Customer Creation**:
   - Tenant and store IDs are stored in customer metadata for future reference:
   ```typescript
   const customer = await stripe.customers.create({
     email: session.user.email,
     name: session.user.name,
     metadata: {
       userId: session.uId,
       tId: session.tId,
       sId: session.sId
     }
   });
   ```

3. **Webhook Processing**:
   - When processing webhook events, tenant and store IDs are extracted from metadata:
   ```typescript
   // Extract from session metadata
   const tId = checkoutSession.metadata?.tId;
   const sId = checkoutSession.metadata?.sId;
   
   // Or from customer metadata if session metadata is unavailable
   if (!tId || !sId) {
     const customer = await stripe.customers.retrieve(checkoutSession.customer as string);
     tId = customer.metadata?.tId;
     sId = customer.metadata?.sId;
   }
   ```

4. **Database Operations**:
   - All subscription database operations filter by tenant and store IDs:
   ```typescript
   // Filtering subscriptions
   const activeQuery = query(
     getCollectionRef(),
     where("tId", "==", session.tId),
     where("sId", "==", session.sId),
     where("status", "==", "active")
   );
   ```

5. **Access Control**:
   - Subscription operations verify tenant and store context before allowing access:
   ```typescript
   // Verify ownership before cancellation
   if (subscription.uId !== session.uId || 
       subscription.tId !== session.tId || 
       subscription.sId !== session.sId) {
     return NextResponse.json({ message: 'Unauthorized access to this subscription' }, { status: 403 });
   }
   ```

### Benefits of Multi-tenancy

1. **Data Isolation**: Each tenant's subscription data is properly isolated
2. **Access Control**: Ensures users can only access subscriptions within their tenant/store context
3. **Hierarchical Structure**: Supports organizational hierarchies with stores within tenants
4. **Flexibility**: Works with both authenticated requests and webhook processing

### Implementation Notes

- The `requestBodyComposer` helper dynamically handles contexts with or without session data
- All subscription-related API endpoints ensure proper tenant and store context is maintained
- For legacy compatibility, functions can fall back to userId-only filtering when tenant/store IDs are not available

---

**Note**: This implementation follows the Stripe-recommended pattern of storing product and price IDs in your application database while letting Stripe handle all payment processing and subscription management through their Checkout Sessions API.
