# DistributionOS Product Routing

Read this reference before classifying or storing a distribution insight. Current repository truth outranks this compact map if the product docs have changed.

## Ledger Choice

Read and improve `__docs__/distribution-operating-system/distribution-operating-system_bible.md`
for reusable doctrine. The routes below are supporting evidence choices, not a
requirement to log every input.

| Input scope | Canonical route | Rule |
| --- | --- | --- |
| MenuList only | `__docs__/menulist-marketing-distribution/menulist-marketing-distribution_external-insight-ledger.md` | Add the next sequential `ML-MKT-EXT-NNN` only when provenance or detailed validation will matter later. |
| Two or more products, portfolio/company strategy, or uncertain product routing | `__docs__/strategy/product-portfolio-distribution-insight-ledger.md` | Add the next sequential `PP-DIST-EXT-NNN` only when a durable product-by-product evidence trail is useful. |
| One non-MenuList product and active work changes | That product's maintained docs | Update only the canonical doc set affected; use the portfolio ledger too when the lesson matters beyond that product or should remain centrally retrievable. |
| Execution, experiment, approval, attribution, outreach, publishing, or outcome evidence for MenuList | `__docs__/menulist-signaldesk/` | DistributionOS may reference the SignalDesk record but must not duplicate it. |

## Responsibility Boundaries

| System | Owns | Does not own |
| --- | --- | --- |
| DistributionOS | Bible curation, source limitations, validation, durable doctrine, selected evidence, product routing, retrieval, revalidation triggers | Article diary, campaign execution, performance attribution, provider operations, publishing, outreach, spend |
| SignalDesk | MenuList source evidence, approved plays, experiments, approval state, attribution, partner/outreach records, outcomes | Portfolio-wide knowledge intake or public product identity |
| CampaignCue | Source-to-reviewed campaign packs and allowed exports | Autonomous provider publishing |
| Website AssetOS | Governed website/media asset production and review | Distribution strategy or channel execution |
| SecurityOS | Security surface/evidence mapping and read-only audit planning | Marketing/distribution decisions |
| PresenceOS | Privacy-first pseudonymous founder public presence | Linking the alias to company/product identity without its explicit gates |

## Supporting Evidence Entry Requirements

Only create a record after the Bible admission test passes and detailed evidence
will be useful later. Such a record must retain:

- status;
- supplied source and source limitation;
- source type;
- retrieval topics;
- explicit use/activation trigger when applicable;
- revalidation trigger;
- claim summary;
- product verdict;
- current decision;
- related canonical truth;
- outcome history.

The status describes the internal decision, not external authority. Revalidate deferred or platform-dependent claims at the moment of use.
