## SECTION A: STRATEGIC INSIGHTS (Future / Vision / Positioning)

### A1. Core Identity & Positioning

- **MenuList is NOT:** a menu tool, QR menu builder, AI menu generator, digital menu SaaS, sync dashboard, marketing tool
- **MenuList IS:** The Canonical Public Business Truth Layer — menu, hours, availability, pricing, status, official link
- **Mental model:** Think DNS for public business offers, not SaaS for menu management
- **Stripe analogy:** Canonical system others reference, not Zapier pushing data everywhere
- **Category:** "Canonical Public Business Truth Infrastructure" — this category does not properly exist yet. Whoever defines it owns it.

### A2. Strategic Decisions Locked

1. **Choice B confirmed:** Global category-defining public truth layer (not India-first profitable company)
2. **Choice B confirmed:** Replacing all scattered menu surfaces with one official link (not fixing rare correctness errors)
3. **Choice B confirmed:** Infrastructure that scales across 50+ countries without rewrites
4. **No API integrations early:** No Instagram, WhatsApp sync, delivery platform sync, aggregator integrations for now
5. **Phase sequencing:** Authority creation → Passive dominance → Selective deep integrations
6. **Distribution model:** Platforms point TO MenuList (not MenuList pushes TO platforms)

### A3. The 3-Layer Future Stack

| Layer | Description | Moat Level |
|-------|-------------|------------|
| **Layer 1 — Canonical Truth Infrastructure** | Menu, hours, availability, pricing, reputation, status, business identity | **HIGH** (consolidates) |
| **Layer 2 — Agent Orchestration** | Personal AI, business AI, consumer assistants | Medium |
| **Layer 3 — Execution Engines** | Ad engines, lead engines, growth automation | Medium |
| **Layer 4 — Tools** | Dashboards, editors, utilities, generic SaaS | LOW (commoditizes) |

MenuList must live in Layer 1. If it drifts to Layer 4, it dies.

### A4. Agent-World Positioning

- **Agents don't replace truth systems. They depend on them.**
- MenuList should be the system agents TRUST and QUERY, not a tool agents bypass
- B2B today → Dual-layer tomorrow: B2B (owner sets truth) + B2A (agents consume truth)
- **Key test:** "If Claude becomes infinitely capable tomorrow, does MenuList still matter?" → YES, because we own the customer-facing truth layer
- **MCP positioning:** Not "an app in MCP" — be the structured truth endpoint agents query

### A5. Competitive Threat Analysis

| Threat | Risk Level | Defense Strategy |
|--------|-----------|-----------------|
| **Google deepening into canonical SMB truth** | HIGH | Become cleaner upstream source Google should read FROM |
| **POS vendors pushing public menu sync** | MEDIUM | Never touch payment flow; be the clean public layer POS cannot be |
| **WhatsApp Business owning storefront identity** | MEDIUM | Become structured truth layer that feeds WhatsApp catalogs |
| **Shopify-like player for physical SMB** | LOW (slow) | Maintain focus on public-offer truth, not commerce |
| **AI agents replacing MenuList** | LOW | Agents can't replace canonical links, QR codes, schemas, PDF exports |

### A6. What Kills This Plan

1. Building too many features / feature creep
2. Becoming "QR menu company" or "AI menu tool"
3. Integrating everything / chasing sync
4. Underpricing (₹199-399 range)
5. Targeting mass low-end SMB
6. Losing positioning clarity
7. Chasing vanity growth metrics
8. Letting menu originate elsewhere (POS, Canva, PDFs)
9. Overbuilding before authority forms

## SECTION C: FEATURE & STABILITY INSIGHTS

### C1. Menu Extraction Engine Role

- **Not the headline** — it's the friction remover / onboarding accelerator
- Messaging: "Send your menu photo or PDF. Your live menu is ready in minutes."
- Creates "wow" moment during sales demo
- Reduces biggest adoption barrier: "I don't have time to set this up"
- Never lead with "AI extraction technology" — that's founder language, not buyer language

### C2. Onboarding Activation

- **Activation = MenuList link live on Google profile** (not account created, not menu uploaded)
- Track: % of paying restaurants using MenuList link on Google
- Onboarding flow: Import menu fast → Generate live link → Guide to replace Google link → Confirm done
- Day 0: menu created → Day 1: Google link replaced → Week 1: QR updated → Week 2: WhatsApp shifts → Month 1: default link

### C3. Infrastructure Validation (Not SaaS Validation)

- Don't over-index on interviews — SMBs cannot articulate infrastructure needs
- **Phase 1 — Truth Replacement Test:** Do they stop sending PDFs? Update MenuList first?
- **Phase 2 — Authority Transfer Test:** Staff told to check MenuList? Used in Google/Instagram?
- **Phase 3 — Dependency Test:** "If MenuList disappeared tomorrow, what breaks?"
- **PMF signals:** Link used daily, sent to customers automatically, used by staff, replaces printed menus, owners update without reminders

### C4. Clean Source Framework (5 Layers)

1. **Structural Cleanliness (Schema Authority):** Strict typing, no string prices, no ambiguous availability
2. **Semantic Cleanliness (Meaning Authority):** Normalize "Veg"/"Vegetarian"/"V" to single canonical enum
3. **Temporal Cleanliness (Version Authority):** Single live version, global version ID, monotonic updates
4. **Sync Cleanliness (Drift Control):** Detect POS/Google/screen mismatches, become drift alarm layer
5. **Output Cleanliness (Machine Readability):** schema.org alignment, deterministic formatting, API-clean

### C5. Data Gravity Moat (What to Track Silently)

| Event Type | What to Track | Why |
|-----------|---------------|-----|
| Item-level | created, updated, deleted, restored | Menu behavior graph |
| Price changes | old/new price, timestamp, frequency | Pricing intelligence dataset |
| Availability | available→unavailable, temp disable, restore | Stock reliability patterns |
| Category/structure | created, deleted, renamed, items moved, reordered | Global menu structure dataset |
| Publish events | version, items changed, publish source, corrections | Operational discipline scoring |
| Store-level truth | hours changed, phone changed, location changed, status | Business reliability graph |

### C6. Event-First Architecture

- **Core principle:** Record event → then update state (not just save final state)
- **Global collection:** `menuEvents` with storeId index (preferred over per-store subcollections)
- **Snapshot on publish:** `menuSnapshots` with compressed JSON, itemCount, timestamp
- **Reliability metrics:** `storeTruthMetrics` updated via nightly job
- **Schema:** `{ tId, sId, entityType, entityId, eventType, oldValue, newValue, changedFields, timestamp, actor, source }`
- **Rules:** Never overwrite history. Every mutation generates event. Server timestamps only. Actor tracking required.
- **Firebase confirmed:** Correct long-term architecture. Phase 1: Firestore ledger → Phase 2: BigQuery mirror → Phase 3: Derived intelligence

### C7. Agent Readiness Metrics (Track Internally)

- Structured data completeness %
- Zero-blank guarantee rate
- Price freshness delta
- Schema validation pass rate
- MenuVersion consistency
- Deterministic rendering rate
- Menu load speed / uptime / cache hit rate
- Render failures / blank menu incidents / link failures

### C8. Source Authority Score (Per Store)

- Is MenuList primary link? (Y/N)
- QR installed? (Y/N)
- Google link connected? (Y/N)
- Website uses MenuList? (Y/N)
- WhatsApp share used? (Y/N)
- Screens active? (Y/N)
