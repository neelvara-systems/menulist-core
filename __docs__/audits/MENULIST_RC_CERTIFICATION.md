## A. Certification scope

- Product: MenuList only.
- Environments: local source, Firebase demo emulators, controlled local browser,
  and the MenuList QA application/tenant hosts after exact build identity is
  verified.
- Production customer data and destructive production testing are excluded.
- Canonica, Answerlattice, CampaignCue, SignalDesk, MyCodex, standalone
  GrowthOS product behavior, KitStamp, and Neelvara behavior is excluded except
  for routing and product-separation checks. MenuList's shipped owner-facing
  Growth Kits add-on remains fully included even though its internal namespace
  uses `growthos`.
- Live Razorpay checkout, credentials, webhooks, captures, refunds,
  settlements, and money movement are excluded. Application behavior around
  the provider boundary is included through source, deterministic tests,
  emulator fixtures, and mock lifecycle states.
- Initial fixture classes: unauthenticated visitor, new/no-tenant user,
  existing owner, staff/restricted actor, public customer, valid/invalid
  tenant and store, enabled/disabled feature, and material subscription and
  lifecycle states derived from current runtime guards. A disposable hosted
  QA owner is now active at tenant `4`, store `4`, with a labelled 72-hour
  zero-value non-payment entitlement and subdomain `qa-rc-144110a18d`. Its
  generated credential is retained only in a mode-600 temporary file for the
  active browser pass; no password appears in the repository, report, terminal
  output, or shell history.

## E. Firebase cost audit

### Confirmed optimization — MLRC-106 disabled scheduler work and finalized leases

- **Observed behavior:** QA reported about 5.2k Function invocations over seven days, matching the every-two-minute maintenance schedule's 5,040 theoretical weekly ticks. The deployed target also reports `ENABLE_MESSAGING_ONBOARDING=false`.
- **Original operation shape:** despite that runtime gate, `messaging_intake` was selected on all 720 daily ticks. Its no-op path performed one lease transaction read/write, one outcome transaction read plus two writes, and one redundant fallback-release read. The active `special_menu_lifecycle` task had the same redundant post-finalization read.
- **Cause:** the provider flag was checked inside the task after task selection, and `finally` always attempted release although `recordTaskOutcome` had already released the owned lease atomically.
- **Change:** disabled tasks are filtered before cadence/lease selection. A finalized outcome records that its lease is already released; fallback release runs only after incomplete finalization. Messaging cleanup/retention stays feature-independent, and special-menu transitions remain every two minutes.
- **Before/after estimate:** 2,880 reads/day and 2,160 writes/day removed; 20,160 reads and 15,120 writes/week; 86,400 reads and 64,800 writes per 30 days. Function invocations remain 5,040/week because the release-critical special-menu lifecycle still owns the two-minute SLA.
- **Correctness:** per-task leases, current-owner verification, stale-owner rejection, retry recovery, outcome state, special-menu public truth, and retention obligations are unchanged.
- **Evidence:** Functions TypeScript build passed; `verify:firebase-scale-cost-closeout` now passes 124 static checks plus both lease emulator suites. The maintenance emulator proves provider-disabled intake is omitted, special-menu lifecycle remains due, stale owners cannot finalize, and the current owner atomically settles/releases its lease.

### Confirmed optimization — MLRC-068 menu-link input preflight
