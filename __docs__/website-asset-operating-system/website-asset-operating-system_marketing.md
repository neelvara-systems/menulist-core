# Website Asset Operating System - Marketing

**Audience:** Internal only  
**Public status:** Internal product architecture only; do not market as a standalone product  
**Purpose:** Explain how to talk about this internally without creating product confusion

---

## Internal Positioning

Website Asset Operating System is the internal product architecture that keeps MenuList and Answerlattice website assets current, governed, and regeneratable.

It turns product truth, brand rules, route structure, and asset slots into a repeatable asset workflow for Codex.

The strongest practical framing is Answerlattice-adjacent: Answerlattice governs support knowledge truth; AssetOS governs product-media truth for founder/operator/developer use.

## One-Liner

Website Asset Operating System lets Codex audit, brief, generate, and review product website assets without the founder repeating product truth and brand context.

## What It Is

- An internal productized asset contract.
- A Codex workflow and skill.
- A manifest and asset-slot system.
- A deterministic audit and review loop.
- A way to prevent stale, oversized, or off-brand assets.
- A media-governance layer that can use Answerlattice product-surface, intake, release, feedback, and drift context as read-only evidence.

## What It Is Not

- Not a public product.
- Not a MenuList owner feature.
- Not an Answerlattice support feature.
- Not GrowthOS.
- Not KitStamp.
- Not a generic screen recorder.
- Not an agency content tool.

## Internal Narrative

The website changes faster than its media. Product screenshots get stale. Launch clips become disconnected from current copy. Public assets drift away from the real product. The fix is not more manual editing. The fix is an asset contract Codex can read.

Website Asset Operating System declares which assets should exist, why they exist, what brand rules they follow, which files satisfy them, and what makes them stale. Codex can then audit the repo, generate briefs, update safe static assets, and flag brand-defining assets for founder review.

## Product Boundary Talking Points

| Concern | Response |
| --- | --- |
| "Can this be a new product?" | Not now. It has practical product shape for founders/operators/developers, especially beside Answerlattice, but no external buyer or independent public runtime is proven. |
| "Is this KitStamp?" | No. KitStamp prepares customer/client content. This governs our own website assets. |
| "Is this GrowthOS?" | No. GrowthOS produces ready-to-use promotional output for SMBs. This produces and audits MenuList/Answerlattice website media. |
| "Is this part of MenuList?" | It supports MenuList marketing, but it is not a MenuList product feature. |
| "Is this part of Answerlattice?" | It is Answerlattice-adjacent internal tooling. It may read Answerlattice truth for media briefs, but it is not Answerlattice support knowledge runtime. |

## Future Commercialization Gate

Only reconsider a public product if all are true:

1. MenuList has stable public presence adoption.
2. Answerlattice website/runtime assets are maintained through this system for months.
3. External teams ask for the same repo-native asset contract.
4. It can be separated without blurring KitStamp or GrowthOS.
5. There is a clear buyer, pricing model, support model, and data boundary.
