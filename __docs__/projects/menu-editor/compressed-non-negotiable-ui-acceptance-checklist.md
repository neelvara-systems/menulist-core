## 1️⃣ Compress into a **Non-Negotiable UI Acceptance Checklist**

### What this is

A **binary checklist** used to judge _any_ digital menu output.

Not a guideline.
Not a suggestion.
A **pass / fail gate**.

### Purpose

This is what your team (and future you) uses to answer:

> “Is this menu allowed to exist?”

If **any item fails**, the UI **cannot ship**.

### Characteristics

- Short
- Brutally objective
- No interpretation
- No design language
- No taste

Example (conceptual, not execution yet):

- Loads usable in <3s → Yes / No
- Price visible without interaction → Yes / No
- Readable in sunlight → Yes / No

### Why this comes first

Because:

- It prevents future drift
- It protects against “but this looks cool”
- It gives you authority to say **no** without debate

This checklist becomes your **final judge**.

## 2️⃣ Translate into **Editor Guardrails**

### What this is

Rules inside the **menu editor** that make it **impossible** for owners to violate the Constitution — even accidentally.

This is not UX.
This is **constraint design**.

### Purpose

Owners should never be able to:

- Hide prices
- Break hierarchy
- Create unreadable menus
- Overload screens
- Make embarrassing outputs

If they _can_, the system has failed.

### Characteristics

- Preventive, not corrective
- Quietly restrictive
- Opinionated defaults
- No “are you sure?” dialogs — just impossibility

Example (conceptual):

- Font sizes can’t drop below legibility threshold
- Accent color can’t be applied to body text
- Image slots capped, not optional

### Why this comes second

Because:

- The checklist defines **what must never break**
- Guardrails enforce it **by design**
- This is how you scale quality without policing users

## 3️⃣ Map Each Article → **Mood + Layout System**

### What this is

A **translation layer** from abstract rules → concrete UI systems.

You already chose:

- **Mood** = emotional tone (clean, bold, warm, premium, clinical, etc.)
- **Layout** = structural behavior (list-first, image-led, compact, catalog, etc.)

This step ensures:

> Every Mood + Layout combo automatically obeys the Constitution.

### Purpose

So you don’t design menus.
You design **systems that produce menus**.

### Characteristics

- No free-form styling
- Mood affects _tone_, not structure
- Layout affects _structure_, not rules
- Constitution overrides both

Example (conceptual):

- A “Dark / Premium” mood still obeys sunlight legibility
- An “Image-led” layout still shows price before scroll
- A “Minimal” mood can’t remove trust signals

### Why this comes last

Because:

- Without the Constitution → moods become subjective
- Without guardrails → layouts become dangerous
- This step locks everything together into one machine
