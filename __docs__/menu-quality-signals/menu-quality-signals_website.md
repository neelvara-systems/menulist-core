## Public Route

Menu Quality Signals is represented on the public website as:

- `/features/menu-quality-validation`

The page uses the public label **Menu Quality Validation**. It should not expose internal names such as Menu Correctness Engine, MCE, repair internals, or scoring implementation.

## Public Positioning

**Core message:** Catch menu issues before customers see them.

Menu Quality Validation supports MenuList's public-truth promise by showing that the owner can find and fix obvious menu problems before publishing the version customers trust.

Approved website claims:

- MenuList can flag missing prices, empty categories, incomplete details, image gaps, and public-readiness issues before publishing.
- Pricing integrity means one owner-approved price can stay connected across MenuList customer surfaces.
- Customer trust indicators include freshness, sections, search, open status, offering type, and clear customer actions where available.
- Validation guides the owner toward fixes; owner approval remains final.

Forbidden public claims:

- Do not call it AI-powered validation, smart validation, autonomous fixing, or automated optimization.
- Do not claim MenuList silently fixes prices/items without owner review.
- Do not promise search ranking, AI answer placement, revenue lift, or customer conversion lift.
- Do not expose exact scores or thresholds unless runtime exposes verified public metrics.

## Page Structure

The page follows `FeatureDetailPage` and `FeatureDetailJourney`:

1. Hero: Catch menu issues before customers see them.
2. Product preview: Menu Check / owner fix next.
3. Signal strip: missing prices, empty categories, item details, photo gaps, owner approval.
4. Sticky journey: Check -> Prevent mistakes -> Fix -> Publish.
5. Support blocks: pricing integrity and public trust indicators.
6. Proof cards: owner decides fixes, visible before publishing, supports public trust, same approved source.
7. Final CTA: upload menu and publish the owner-approved version.
