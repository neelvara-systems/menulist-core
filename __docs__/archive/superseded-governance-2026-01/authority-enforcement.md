**Created:** January 11, 2026  
**Status:** 🔒 **LOCKED — NO EXCEPTIONS**  
**Authority:** Founder Only  
**Audience:** Sales, Support, Engineering, Everyone

---

## Purpose

This document defines **what MenuListAi will NEVER do** — regardless of customer pressure, deal size, or team opinion.

These are not guidelines. These are **hard stops**.

> "If you break these rules to close a deal, you've sold a product that doesn't exist."

---

## Part 1: Forbidden Promises

These statements may **NEVER** be made to customers. Period.

| ❌ Forbidden Promise                           | Why It Kills Authority                           |
| ---------------------------------------------- | ------------------------------------------------ |
| "We can customize the recommendations for you" | Creates dual authority                           |
| "You can control what appears on the screen"   | Undermines system intelligence                   |
| "We can add that feature for you"              | Promises non-existent roadmap                    |
| "The AI learns YOUR preferences"               | Wrong mental model (it learns CUSTOMER behavior) |
| "You can turn off the AI recommendations"      | Makes the core optional                          |
| "We can integrate with your POS/CRM/ERP"       | We're not an integration layer                   |
| "We'll add a dashboard for that"               | Dashboard creep                                  |
| "Our team will manually review your menu"      | Creates service dependency                       |
| "You can schedule what shows when"             | Owner-controlled scheduling kills intelligence   |
| "We guarantee X% increase in sales"            | Unverifiable ROI promise                         |

### If a Customer Asks for Any of These

**Correct Response:**

> "MenuList works best when it runs quietly. The system learns from your customers, not your preferences. That's what makes it trustworthy."

**Then stop talking.**

If they push harder:

> "I understand. MenuList may not be the right fit for businesses that want manual control. We believe in system confidence, not owner micromanagement."

**Then let them decide.**

Walking away protects the brand.

## Part 2: Forbidden Explanations

These explanations may **NEVER** be offered — even if the customer asks.

| ❌ Forbidden Explanation                   | Why It's Dangerous           |
| ------------------------------------------ | ---------------------------- |
| "It recommended X because of Y algorithm"  | Invites debate about logic   |
| "The confidence score is calculated by..." | Creates false precision      |
| "Your data shows that customers prefer..." | Owner will argue with data   |
| "We use Gemini/GPT/AI model X"             | Tech names invite skepticism |
| "The system is still learning"             | Suggests uncertainty         |
| "We'll fix that in the next version"       | Promises unscheduled work    |
| "Other businesses see Z% improvement"      | Unverifiable comparisons     |

### If a Customer Asks "How Does It Work?"

**Correct Response:**

> "MenuList watches what your customers notice and recommends what helps them decide faster. If it's not confident, it stays quiet."

**That's it.** No diagrams. No architecture. No AI buzzwords.

### If a Customer Asks "Why Did It Show X?"

**Correct Response:**

> "Because that's what helps customers decide right now. If the situation changes, so will the recommendation."

**Never say:** "Because the confidence score was 0.73 based on behavior signals..."

## Part 3: Forbidden Actions

These actions may **NEVER** be taken — even under pressure.

| ❌ Forbidden Action                                            | Consequence               |
| -------------------------------------------------------------- | ------------------------- |
| Manually override a recommendation for a specific customer     | Fire offense              |
| Promise a feature on the roadmap                               | Requires founder approval |
| Share internal confidence scores with customer                 | Creates false precision   |
| Offer custom pricing below ₹999/month                          | Devalues product          |
| Disable AI recommendations for any reason                      | Removes core value        |
| Add a customer to a "beta" or "pilot" without founder approval | Creates precedent         |
| Share screen heartbeat data with owner                         | Creates anxiety           |
| Commit to a timeline for any fix or feature                    | Only founder commits      |

### If Engineering Gets a "Just This Once" Request

**Correct Response:**

> "I can't make that change without founder approval. Our system is designed to be consistent across all customers."

**Then escalate to founder.** Let founder say no.

## Part 4: Exact Redirect Phrases

When you need to say no without damaging the relationship.

### Redirect: "Can You Add X Feature?"

> "We intentionally keep MenuList simple. Adding features usually hurts more than it helps. But I'll note your feedback."

**Then move on.** Don't negotiate.

### Redirect: "Can I Control What Shows?"

> "You can override temporarily, but most owners stop doing that after a week because the system handles it better."

### Redirect: "Can You Explain the Recommendation?"

> "The system shows what helps customers decide. The specifics change daily — that's normal."

### Redirect: "We Need Integration with X"

> "MenuList is designed to work independently. We don't integrate with POS or CRM systems — that keeps it simple and reliable."

### Redirect: "Your Competitor Does Y"

> "We focus on doing one thing well: helping customers decide. If you need Y, they might be a better fit."

**Never compete on features.** Compete on confidence.

### Redirect: "Can I Get a Discount?"

> "₹999/month is the price for all customers. We don't negotiate because the product is the same for everyone."

## Part 6: Escalation Rules

### When to Escalate to Founder

| Situation                                   | Escalate?            |
| ------------------------------------------- | -------------------- |
| Customer asks for feature not on roadmap    | ✅ Yes               |
| Customer offers 10x price for custom work   | ✅ Yes               |
| Customer is enterprise/chain (5+ locations) | ✅ Yes               |
| Customer threatens public complaint         | ✅ Yes               |
| Customer found a real bug                   | ⚠️ Engineering first |
| Customer wants discount                     | ❌ No — answer is no |
| Customer wants explanation of AI            | ❌ No — use redirect |

### How to Escalate

1. Document the exact request
2. Document your redirect response
3. Document customer reaction
4. Send to founder with: "Request that exceeds my authority. Awaiting decision."

**Do not promise "I'll check with my team."**

Say: "I can escalate this, but I can't promise any outcome."

## Part 7: Failure Narrative (Centralized)

**This is the ONE sentence that explains ALL failures.**

> "MenuList prefers to go quiet rather than show something it's not confident about."

### Use This When:

| Situation                                          | Response                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Screen shows nothing                               | "MenuList prefers to go quiet rather than show something it's not confident about." |
| Recommendation disappeared                         | Same                                                                                |
| Today tab is empty                                 | Same                                                                                |
| Decision Block says "Popular" but item seems wrong | Same                                                                                |
| Owner says "it was better yesterday"               | Same                                                                                |

**Never:**

- Apologize for silence
- Promise it will "get better"
- Explain the confidence calculation
- Offer to manually fix it

**Silence is a feature, not a bug.**

## Part 8: Enforcement

### Who Enforces This

- **Sales:** Sales lead reviews all closed deals
- **Support:** Support lead reviews all escalations
- **Engineering:** Tech lead reviews all exception requests
- **Everyone:** Founder reviews quarterly

### Consequences

| Violation                    | Consequence                |
| ---------------------------- | -------------------------- |
| First offense (minor)        | Written warning            |
| First offense (major)        | Immediate review           |
| Second offense               | Role change or termination |
| Promising roadmap features   | Immediate founder review   |
| Manual override for customer | Termination                |

This is not bureaucracy. This is **survival**.
