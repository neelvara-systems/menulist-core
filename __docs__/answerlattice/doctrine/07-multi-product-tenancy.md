> **Authority:** Founder decision. PERMANENT. No phases. No deferral.
> **Scope:** All products: MenuList, Answerlattice, GrowthOS, KitStamp, SurfaceOS
> **Decision:** Every product integrates with Answerlattice the same way — via Answerlattice Client Token (CCT). No exceptions. MenuList included.

---

## The Problem

Multiple products share the same Firestore. `tId=1` in MenuList (Reddy's Restaurant) collides with `tId=1` in Answerlattice (MenuList as client). A multi-product platform needs product-level namespace isolation and a universal integration model.

---

## Foundational Principles

1. **Identity:** `pId / tId / sId / docId` = Product → Tenant → Scope → Resource
2. **Universal integration:** Every product uses the same token-based pattern to connect with Answerlattice. No special embedded path.
3. **Clean boundary:** Answerlattice NEVER reads another product's session directly. Always via token.

Every Answerlattice document carries two layers:

### Root Level — Answerlattice Ownership

| Field | Value  | Meaning                                          |
| ----- | ------ | ------------------------------------------------ |
| `pId` | `"AL"` | This is an Answerlattice document                      |

| `sId` | number | Answerlattice client scope ID (from client registry)  |

### `sourceContext` — Who Created This and From Where

| Field   | Required           | Meaning                                  |
| ------- | ------------------ | ---------------------------------------- |
| `uId`   | Always             | User ID from source session              |
| `name`  | Always             | User name from source session            |
| `email` | Always             | User email from source session           |
| `phone` | Always             | User phone from source session           |
| `pId`   | Cross-product only | Source product ID (`"ML"`, `"GR"`, etc.) |
| `tId`   | Cross-product only | Tenant ID in source product scope        |
| `sId`   | Cross-product only | Store ID in source product scope         |

## Universal Integration: Answerlattice Client Token (CCT)

Every product integrates with Answerlattice the same way: via a signed JWT called **Answerlattice Client Token (CCT)**. No special embedded path. No session reading. One universal pattern.

### Answerlattice Client Registry

Every product onboards with Answerlattice and gets registered as a client:

```
answerlattice_clients collection:
  { clientId: "ml_001", clientName: "MenuList", tId: 1, sId: 1, secretKey: "al_sk_xxxx", sourcePId: "ML", active: true }
  { clientId: "rsk_001", clientName: "Respark", tId: 2, sId: 1, secretKey: "al_sk_yyyy", sourcePId: null, active: true }
```

- `tId`/`sId` = this client's identity in Answerlattice scope
- `secretKey` = used to sign and verify CCT tokens
- `sourcePId` = source product ID (null for direct clients like Respark)
- MenuList is client #1 — onboarded from day one

### CCT Token Structure

Signed JWT generated by client's backend, verified by Answerlattice:

```json
{
  "clientId": "ml_001",
  "traceId": "req_9b2d13f4",
  "requestId": "rid_8k2j4m",
  "pId": "ML",
  "tId": 42,
  "sId": 3,
  "uId": 111,
  "name": "John",
  "email": "john@reddys.com",
  "phone": "2098209",
  "iat": 1709500000,
  "exp": 1709503600
}
```

- `clientId` — identifies which Answerlattice client (looks up verification secret)
- `traceId` — UUID for end-to-end request tracing across session → CCT → document → audit log
- `requestId` — idempotency key to prevent duplicate operations on retry
- `pId`, `tId`, `sId` — source product scope (optional for direct clients)
- `uId`, `name`, `email`, `phone` — user identity (always present)

### Answerlattice Verification Flow

1. Read `clientId` from token
2. Look up client in registry → get `secretKey`, `tId`, `sId`
3. Verify token signature with `secretKey`
4. Build document root: `pId='AL'`, `tId=client.tId`, `sId=client.sId`
5. Build `sourceContext` from remaining token fields
6. Build typed `AnswerlatticePlatformContext` for downstream code

### Platform Context Envelope

After CCT is decoded and verified, all downstream Answerlattice code receives a typed context object. This is the ONLY way Answerlattice features access identity.

```ts
interface AnswerlatticePlatformContext {
  traceId: string;
  requestId: string;
  client: { clientId: string; tId: number; sId: number };
  source: {
    pId?: string;
    tId?: number;
    sId?: number;
    uId: number;
    name: string;
    email: string;
    phone?: string;
  };
  issuedAt: number;
}
```

- `AnswerlatticeClientProvider` generates CCT from session and exposes decoded `AnswerlatticePlatformContext` via React context
- All Answerlattice DAL writes, audit logs, and analytics include `traceId` for end-to-end debugging
- `requestId` checked before write operations to prevent duplicates on retry (idempotency)

## Integration Flows

### Embedded Client (MenuList — same codebase)

```
User logs into MenuList (NextAuth session)
  → User navigates to Answerlattice feature (tickets, KB, chat)
  → AnswerlatticeClientProvider generates CCT from session:
      clientId: "ml_001"
      pId: "ML", tId: session.tId, sId: session.sId
      uId: session.uId, name, email, phone
      Signed with MenuList's client secret
  → Answerlattice feature reads CCT from context
  → Answerlattice verifies → extracts identity → creates document
```

### External Client — Redirect (Respark, future)

```
Respark user clicks "Help" in Respark app
  → Respark backend generates CCT:
      clientId: "rsk_001"
      uId, name, email, phone (from Respark session)
      No pId/tId/sId (direct client)
      Signed with Respark's client secret
  → User redirected to: answerlattice.com/help?token=eyJhbG...
  → Answerlattice verifies → extracts identity → creates document
```

### External Client — Widget (Respark, future)

```
Respark help page loads Answerlattice widget:
  <script>
    window.answerlatticeSettings = { token: "eyJhbG..." };
  </script>
  <script src="answerlattice.com/widget.js"></script>
  → Answerlattice widget reads token
  → Answerlattice verifies → extracts identity → creates document
```

## Firebase Project Topology

### Current State

Single Firebase project: **`ecomsai`**. All products share one Firestore, Auth, Storage, Realtime Database, Cloud Functions, Vertex AI, App Check. One billing account.

Answerlattice collections already prefixed `answerlattice_*` (9 collections). MenuList collections unprefixed (legacy).

### Decision: Separate Answerlattice Firebase Project From Day One

**Two Firebase projects. Not deferred. From day one.**

```
Project 1: "ecomsai" (MenuList Ecosystem)
  → MenuList, SurfaceOS, GrowthOS, KitStamp
  → Same user base, same tenants, tightly coupled data

Project 2: "answerlattice" (Answerlattice Standalone)
  → Answerlattice only
  → Own Auth, own billing, own scaling, own security rules
```

### Why Answerlattice Gets Its Own Firebase Project

1. **Own Auth** — External clients (Respark etc.) have users that do NOT exist in MenuList's Firebase Auth. Answerlattice needs a separate Auth instance.
2. **Own billing** — To price Answerlattice for clients, we must know its actual Firebase costs. Commingled billing makes this impossible.
3. **Own scaling** — Support load from multiple SaaS clients is unpredictable. A spike in Respark's tickets must not affect MenuList's quotas.
4. **Own security rules** — Answerlattice rules only handle Answerlattice collections. Simpler to audit. No risk of exposing MenuList data.
5. **Independent failure** — If Answerlattice's Firebase has an outage, MenuList continues. And vice versa.
6. **Sellable independently** — If Answerlattice is ever sold or licensed, it's already a self-contained Firebase project with zero MenuList dependencies.

### Why MenuList Ecosystem Stays Together

SurfaceOS, GrowthOS, KitStamp are extensions of MenuList:

- Same user base (SMB owners logged in via MenuList Auth)
- Same tenant data (`tId`/`sId` from MenuList scope)
- Tightly coupled (GrowthOS reads MenuList project data, KitStamp reads menu data)
- No external client use case
- Separating them creates cross-project complexity with zero benefit

### Firebase Services Per Project

| Service         | ecomsai (MenuList)                    | answerlattice (Answerlattice)                              |
| --------------- | ------------------------------------- | ------------------------------------------------ |
| Firestore       | MenuList + future product collections | `answerlattice_*` collections only                    |

### Cross-Project Communication

MenuList and Answerlattice are separate Firebase projects but same Next.js codebase:

1. **CCT token** — MenuList generates signed token from session. Answerlattice verifies using client registry. No direct cross-Firestore reads.
2. **Shared codebase** — Both Firebase clients in same app. AnswerlatticeClientProvider bridges the two.
3. **No cross-project queries** — MenuList features read MenuList Firestore. Answerlattice features read Answerlattice Firestore. Never mixed.

### Migration Plan

1. Create Firebase project `answerlattice` in GCP console
2. Enable Firestore, Auth, Storage in new project
3. Export `answerlattice_*` collections from `ecomsai`
4. Import into `answerlattice` Firestore
5. Backfill `pId = 'AL'` on all imported documents
6. Add Answerlattice env vars to Vercel
7. Create `answerlatticeFirebaseClient.ts` and `answerlatticeFirebaseAdmin.ts`
8. Update all 9 Answerlattice DAL files to use `answerlatticeFirebaseClient`
9. Delete `answerlattice_*` collections from `ecomsai` after verification
10. Update security rules in both projects

### Why `pId` Still Matters With Separate Projects

`pId` remains critical even with separate Firestore instances:

- **Within Answerlattice Firestore:** `pId = 'AL'` confirms this document belongs to Answerlattice. If Answerlattice ever serves multiple product verticals internally, `pId` distinguishes them.
- **In CCT tokens:** `sourceContext.pId` tells Answerlattice which product the request came from (`"ML"`, `"GR"`, etc.).
- **In analytics/reporting:** Cross-product dashboards can query by `pId` to aggregate data from both Firestores.
- **Future-proof:** If projects are ever merged back (unlikely but possible), `pId` prevents collision.

## Rejected Approaches (Documented)

1. **Full REST API** — Too heavy. Token + DAL is sufficient for embedded mode.
2. **localStorage/cookies for external clients** — Cross-domain blocked. Token in URL/widget instead.
3. **`canonTenantId`/`canonWorkspaceId` renaming** — `pId` already disambiguates. No rename needed.
4. **Flattened `sourceProductId`/`sourceTenantId`** — Firestore supports nested queries. `sourceContext` object is cleaner.
5. **Cloud Run for Answerlattice** — Same Next.js app with two Firestores is sufficient now.
6. **Monorepo app restructuring** — One Next.js app. Separation at Firebase + code level, not app level.
7. **`schemaVersion` on documents** — Not live. Additive fields + migration scripts suffice.

## Rules (PERMANENT)

1. **Token-first, universal.** Every product integrates with Answerlattice via CCT. No exceptions. No special embedded path.
2. **`pId` is MANDATORY** on every document. 2-char uppercase string.
3. **`tId`/`sId` keep their names everywhere.** No `tenantId`, `scopeId`, `productId`. Always `tId`, `sId`, `pId`.
4. **`sourceContext` is required** on all Answerlattice documents from clients. User identity always present; source product scope only for cross-product.
5. **Answerlattice never reads another product's session directly.** Always via CCT → `AnswerlatticePlatformContext`.
6. **Client registry from day one.** MenuList is client #1. Every new product/client gets registered.
7. **Separate Firebase projects.** Answerlattice gets its own Firebase project from day one. MenuList ecosystem (SurfaceOS, GrowthOS, KitStamp) stays in `ecomsai`. No cross-project Firestore queries.
8. **`traceId` on every CCT and every Answerlattice document.** End-to-end request tracing from session → token → document → audit log.
9. **Idempotency via `requestId`.** Cross-product write operations (ticket creation, chat, feedback) must include `requestId`. Answerlattice checks for duplicates before writing.
10. **Graceful degradation.** If Answerlattice Firestore is unavailable, MenuList must continue working. Help center shows "temporarily unavailable". Answerlattice features wrapped in try/catch with fallback UI. Never crash MenuList due to Answerlattice failure.
11. **Identity consistency across ALL products.** Every future product (SurfaceOS, GrowthOS, KitStamp) MUST use `pId`/`tId`/`sId`. No custom identity fields (`accountId`, `locationId`, `orgId`). The platform identity model is universal and non-negotiable.
12. **This document is the sole authority.** All tenancy, integration, and Firebase topology decisions reference this.
