# Answerlattice Staff Access Control Implementation

> Status: Implemented
> Last updated: 2026-07-19
> Feature audit: Feature 31 of 44

## Main Code Paths

- `src/constants/answerlattice/permissions.ts` defines Answerlattice permission keys, labels, default roles, route-permission mapping, and role normalization. Built-in role projection uses stable system provenance rather than the current reader and current time. Normalization clears `canAssignRoles` unless `canManageTeam` is also true because member-role mutation and the Team route both require team authority.
- `src/lib/answerlattice/accessControl.ts` resolves the active Answerlattice access context from session, Answerlattice user doc, store doc, and `stores/{sId}.answerlatticeRoles`. Role normalization is pure on this read path: it performs no role backfill write, and unknown/inactive roles fail closed instead of inheriting Support Staff permissions.
- `src/providers/answerlatticeAccessProvider.tsx` exposes the resolved access context to Answerlattice dashboard components. It loads `/api/answerlattice/access` with no-store cache, same-origin credentials, and manual redirect handling, then requires a 64 KB bounded `{ access }` response with a valid permission context before dashboard state updates. The load identity includes the current session user/workspace/role/expiry, and a monotonic latest-request guard prevents an older workspace response or an unmounted effect from replacing current access state.
- `src/components/answerlattice/AnswerlatticeDashboardLayout.tsx` blocks permission-mismatched routes and waits for Answerlattice Firebase Auth sync. Sync failures use bounded `answerlattice_dashboard_firebase_auth_sync_failed` diagnostics instead of raw browser console errors.
- `src/components/answerlattice/AnswerlatticeSidebar.tsx` hides nav entries that the current role cannot use.
- `src/components/templates/answerlattice/AnswerlatticeTeamAccess.tsx` renders members, role editing, activation/deactivation, password/passcode reset, force sign-out, and remove controls. Enabling role assignment also enables its team-access prerequisite; removing team access clears role assignment before save. Failed load/member/role actions use fixed local dashboard copy instead of raw staff API or browser exception text.
- `src/lib/answerlattice/staffAccessServer.ts` owns all staff and role mutations. Staff/team action rate-limit keys hash the actor or request-IP segment through the shared Answerlattice limiter-key helper before calling Upstash, so raw staff user IDs and request IPs are not stored in provider key names.
- `src/lib/answerlattice/staffAccessContracts.ts` is the runtime contract for tenant scope, exact workspace IDs, duplicate-free `stores[]`, primary membership selection, and canonical root access fields. List and access-context projection use the requested workspace membership rather than the user's primary workspace role.
- `src/lib/answerlattice/staffClaimsContracts.ts` projects only active validated membership state into Auth claims. It normalizes platform authority, preserves a still-valid current claim workspace, builds a deterministic full claim-state signature, and guards the documented 1,000-byte Firebase custom-claim limit in contract tests.
- `src/lib/answerlattice/staffAccessTransactions.ts` owns membership create/update/remove, last-owner protection, active-role admission, and role-in-use query guards. Store, user, and relevant bounded user-query reads are in the same Firestore transaction as the write.
- `src/lib/answerlattice/staffAccessBridge.ts` synchronizes default Firebase `productAccounts.AL` with a monotonic `accessRevision`. Stale protection uses the maximum nested-account and legacy Answerlattice-root revision. Exact equal state is read-only, equal revisions may repair profile/login/canonical alias drift, and non-Answerlattice root product scope is preserved.
- Default-auth bridge scope is fail-closed across every present compatibility alias. Nested account and root tenant/store aliases must agree before reuse; missing product identity with contradictory root scope is preserved rather than overwritten. Product-account erasure requires exact tenant-alias agreement plus provably empty direct and list membership state, so malformed or hidden membership evidence cannot be interpreted as an empty account.
- Staff list, last-owner, and role-in-use queries apply `tenantId` before `storeIds array-contains` and before their bounded scans. The list reads a 501st sentinel and rejects overflow rather than silently omitting a member; owner/role safety scans accept at most 500 documents. Role-in-use includes inactive identities because their retained membership remains a live reference. The matching composite index exists in dedicated and shared index files, so another tenant with the same numeric workspace ID cannot consume the cap.
- Staff creation requires a UUID request ID. The owner-passcode path derives a stable managed login identity and every path stores a scoped payload fingerprint. A lost response can be replayed without creating another membership. Changed content or a delayed replay after that membership was removed fails with `IDEMPOTENCY_CONFLICT`; re-add requires a new request. A replay never invents/re-exposes the original passcode or resends the initial setup email and instead directs the owner to the explicit reset action.
- Custom role creation uses a deterministic role ID plus stored request fingerprint. An exact lost-response replay returns the existing role, while changed content with the same request ID fails with `IDEMPOTENCY_CONFLICT`. Role array mutation is transaction-backed, rejects duplicate names, persists custom roles only, and caps custom roles at 25 so concurrent owners cannot overwrite one another or grow the store document without a bound. Role deactivation and assignment read each other's durable state inside their transactions, so both conflicting operations cannot commit. Built-in roles are immutable runtime projections because the rulesets carry matching compatibility defaults. A custom-role edit transaction captures all retained assignees, including inactive accounts, and the server refreshes and revokes their permission claims in bounded groups.
- Staff/team JSON mutation bodies are capped at 16KB through `readBoundedJsonBody()` before the existing Zod schemas run. Malformed or oversized staff mutation bodies fail before JSON parsing can allocate unbounded request payloads.
- Answerlattice staff user ID boundary: staff update, remove, password/passcode reset, and force sign-out validate request `userId` values through `src/lib/answerlattice/staffUserIdBoundary.ts` before user document lookup. The shared helper rechecks IDs before `users/{userId}` refs, and staff create/default-auth bridge paths validate derived Answerlattice/default Firebase user IDs before writes.
- Answerlattice management access scope boundary: `src/lib/answerlattice/accessControl.ts` treats the shared session scope as the only route-session source, then normalizes persisted `stores`, `users`, `stores[]`, and `answerlatticeRoles` tenant/store fields with `normalizeAnswerlatticeScopeDocumentId()` before granting access or role permissions. Malformed persisted scope and duplicate custom-role authority fail closed before management context is returned. The access read never mutates role storage.
- `src/lib/answerlattice/staffAccessClient.ts` owns client fetch helpers for the Team Access page. Staff list, staff mutation, password reset, force sign-out, and role mutation browser calls use no-store cache, same-origin credentials, and manual redirect handling before response parsing. Failed staff API responses keep the route status/code for policy handling but throw fixed local copy instead of raw route response text. Responses use a 1 MiB bounded reader and validate nested memberships, duplicate-free aligned workspace IDs, current-workspace role agreement, tenant/store agreement across users and roles, mutation user identity, role objects, and every optional field before Team Access callers continue.
- `src/lib/answerlattice/accessControl.ts`, `/api/answerlattice/access`, and `staffAccessServer.ts` share private `no-store, max-age=0` plus `nosniff` response headers. This includes denials and the mutation responses that may carry one-time staff login details.
- `src/components/templates/main-app/users/StaffLoginDetailsContent.tsx` and `src/lib/staffManagement/shareLoginDetails.ts` are reused for Answerlattice owner-passcode sharing so the one-time passcode UX stays aligned with MenuList.

- `POST /api/answerlattice/staff/password-reset`

## Login Modes

- Email members receive a password setup email when first created.
- Email creation does not generate an unused alternate staff ID, avoiding the default/Answerlattice uniqueness queries. The explicit Login reset path generates one only when temporary credentials are requested.
- A successful create replay does not repeat the setup-email provider call. If the original delivery failed or was lost, **Login** is the explicit recovery action.
- Password setup email calls use the fixed Firebase Auth `sendOobCode` host/path, encode the local API key with `URLSearchParams`, reject malformed local API keys before contacting Firebase Auth, and use manual redirect handling plus a timeout for the provider request.
- Password reset email provider failures, timeouts, and rejected responses log bounded `answerlattice_staff_password_reset_provider_*` diagnostics and return the fixed `password_reset_email_failed` response marker; Firebase Auth provider text is not retained for UI reuse.
- Owner reset creates a one-time temporary passcode and revokes refresh access for both email-backed and owner-passcode members, matching the MenuList staff model without claiming instant deletion of already-issued ID tokens.
- Owner-passcode members receive an internal staff login id plus temporary passcode.
- The add-member modal keeps one request ID for the life of the open attempt and clears it only after success or cancellation. Retrying a failed network request therefore reaches the same server identity.
- Phone number, country code, dial code, staff login id, and auth mode follow the MenuList staff shape so reset and share flows behave consistently.
- Owner-triggered password/passcode resets and force sign-out revoke Firebase refresh tokens and refresh Answerlattice permission claims.
- Self-removal and last-owner guards use coded local policy errors before returning fixed client messages; self matching covers both project-local user ID and normalized email identity and does not branch on raw exception text.
- Default auth users receive/refresh `productAccounts.AL` so NextAuth can resolve Answerlattice scope.
- Separate Answerlattice Firebase Auth receives Answerlattice permission custom claims for direct client DAL rules.
- Workspace removal returns `removed: true`; Team Access removes the row for the current workspace even when the identity remains active in another workspace.
- Multi-workspace activation controls are disabled for workspace actors and rejected transactionally because the current `active` field is account-global. Platform administrators retain an explicit account-wide recovery control that is carried into the transaction rather than inferred from caller input.
- Platform account-wide deactivation collects every Owner membership on the identity and runs the bounded last-owner query for each affected workspace before writing.
- Multi-workspace login reset and force-sign-out controls are disabled for workspace actors and rejected server-side because credentials and refresh tokens are account-global. Platform administrators retain the explicit account-wide recovery path.
- Claim synchronization reads current Answerlattice user state, preserves the Auth user's current workspace when it remains a validated membership, otherwise selects the affected or primary membership, and emits a singleton selected-workspace list. It compares revision and core scope claims, normalizes unsupported platform roles to `USER`, and revokes refresh tokens when claims/disabled state changes or an explicit reset, sign-out, removal, or custom-role refresh requires it. After a claim write it rereads both the user and selected store and compares a deterministic signature covering account status, tenant, workspace, role, platform role, admin authority, and every permission. Revision or signature drift retries within the existing three-attempt bound; exhaustion returns `ANSWERLATTICE_STAFF_CLAIM_SYNC_STATE_CONFLICT`. Missing or malformed user state fails the projection. A missing/inactive workspace or inactive account emits an `inactive` role with no default-role fallback; inactive accounts also emit no workspace list, admin claim, or role permission.
- `/api/auth/set-claims` derives target admission, selected role, singleton selected-workspace claim list, and access revision from strict active `stores[]`, then reuses its already-authorized canonical store snapshot for custom-role permission resolution. This avoids both top-level membership widening and a second Firestore read/between-read role race.
- If Firebase Auth identity creation succeeds but the membership transaction rejects, compensation deletes the Auth identity only when no Answerlattice user document adopted that Firebase UID; concurrent successful adoption is preserved.
- Default Auth revocation resolves the target by normalized email whenever email exists, so stale UID metadata cannot revoke another identity or skip the real account. Password reset uses the same email authority.
- Staff create, update, removal, login-reset, and force-sign-out projections use an all-settled post-commit repair runner. Every independent bridge/claim/revocation action is attempted, failures return `STAFF_ACCESS_SYNC_FAILED`, and a removal retry uses the durable removal marker to finish projections without restoring access.
- `/api/auth/set-claims` validates a supplied default-project UID/email match before creating or mutating the Answerlattice Auth identity. Concurrent Auth get-or-create races re-read the winning email identity.

## External Firebase Auth Contract

Verified against official Firebase documentation on 2026-07-19:

- [Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions): Firebase ID tokens are short lived with an approximately one-hour lifetime; revoking refresh tokens prevents new ID tokens but does not retroactively erase an already-issued token.
- [Control Access with Custom Claims](https://firebase.google.com/docs/auth/admin/custom-claims): updated claims appear on a new sign-in, reauthentication, token refresh/expiry, or an explicit forced token refresh; custom-claim payloads must remain at or below 1,000 bytes.
- [Security Rules and Authentication](https://firebase.google.com/docs/rules/rules-and-auth): Firestore and Storage rules consume the claims present in the authenticated token.

Answerlattice therefore refreshes/revokes after material access changes, keeps claims selected-workspace scoped, and avoids an extra Firestore revocation lookup on every protected request. This is a deliberate cost/complexity boundary, not an instant-revocation guarantee.
