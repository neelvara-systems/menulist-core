### Writes

| Operation | Collection | Trigger | Frequency | Docs Written | Notes |
|-----------|-----------|---------|-----------|-------------|-------|
| Increment daily counters | `analytics/{tId}_{sId}_{projectId}_daily_{businessDate}` | Customer menu interactions | Coalesced for passive events; immediate for final actions | 1 per flush/action | Events: MENU_VIEW, ITEM_VIEW, ITEM_CLICK, DECISION_BLOCK_CLICK, SEARCH, UNAVAILABLE_ITEM_ATTEMPT, MENU_ACTION_CLICK. The `{businessDate}` key is resolved from `storeTimeZone` + `businessDayEndTime`. | Aggregate daily stats | `analytics` (aggregated docs) | Shared timezone-aware nightly scheduler | Daily per store-local date | 1 per active project with activity, plus rollup docs when needed | `computeDecisionBlocksScores` runs OBP first, then customer/menu analytics in one locked store/date pass. Summary updates are idempotent and skipped if the date is already aggregated. |
| Write owner dashboard read model | `analytics/{tId}_{sId}_{projectId}_dashboard_summary` | Shared timezone-aware nightly scheduler | Daily per settled project/surface | 1 | Stores settled owner-facing overview, daily, weekly, monthly, all-time, and compact rolling daily rows so dashboards do not rebuild from daily docs. The menu read model preserves source quality, UTM source/medium/campaign/content, top items/categories, actions, search demand, unavailable demand, languages, filters, and Smart Picks detail for desktop/mobile parity. | Write owner action receipt | `analytics/{tId}_{sId}_{projectId}_dashboard_summary.ownerActionReceipts` | Owner taps `Mark done` | Owner-initiated only | 1 | Stores a capped owner-side receipt in the existing dashboard summary doc. This does not add public customer tracking and does not create a separate receipt collection. |
| Write intelligence input read model | `analytics/{tId}_{sId}_{projectId}_intelligence_7d` | Shared timezone-aware nightly scheduler | Daily per settled menu project | 1 | Stores compact 7-day item analytics used by Decision Blocks and Menu Intelligence, avoiding repeated 7-day daily-doc reads during the same scheduler flow. |
| Settlement state / lock | `platformSummary/nightlyState_*`, `platformSummary/nightlyLock_*` | Shared timezone-aware nightly scheduler | Per due store/date | 1 state doc + 1 lock doc | Prevents duplicate processing and enables missed-day catch-up from the last settled local date. The completed state also stores a compact store-level analytics index: active project ids, settled surfaces, and summary doc ids. |

None — analytics data is append-only / increment-only.

## Cloud Functions

| Function | Trigger | Frequency | Duration | Memory | Notes |
|----------|---------|-----------|----------|--------|-------|
| `computeDecisionBlocksScores` | Scheduled (hourly, timezone-aware) | 24x/day scheduler, but each store settles once at its local nightly hour | 10-30s typical per batch | 256MB | Runs decision blocks, menu intelligence, OBP analytics, and customer analytics in one store-scoped nightly flow. |

## Public Write Path

Anonymous customer analytics no longer writes directly to Firestore from the browser. Public menu, OBP, and Customer App events still coalesce in the local queue, then flush to `POST /api/public/analytics/track` with same-origin credentials, no-store cache policy, keepalive, and manual redirect handling before accepting the route acknowledgement. The route is IP-rate-limited, rejects JSON bodies above 64KB before schema validation, validates the tenant/store/project target, rejects inactive/deleted/platform-blocked stores and platform-blocked tenants, enforces the store-owned analytics preferences, resolves the business-day bucket from the stored store timezone/cutoff, strips Decision Blocks counters when that category is disabled, and writes the same daily analytics document with Firebase Admin SDK. Firestore rules stay authenticated-only for `analytics/{docId}`.

## Cost Discipline Rules

- **Allowed:** explicit, low-frequency intent signals such as menu opens, item opens, unique search terms, recommendation taps, unavailable-item taps, final CTA clicks, anonymous session milestones, item-derived category interest, and open/closed/unknown state attached to final action writes.
- **Rejected:** scroll depth, per-keystroke search, hover tracking, category scroll/open events, heartbeat/session pings, image impressions, and any passive event that would create steady write volume.
- **Search rule:** one unique search term per store/project/session. This preserves demand signals without turning typing into write spam.
- **Write coalescing rule:** public customer counters queue for a 15-second client-side window or 20 queued events and flush together. The queue is persisted in browser storage and retried on the next page load within the correction window. Final conversion actions are added to the local queue immediately, but they do not bypass coalescing with a separate Firestore write.
- **Session milestone rule:** `menuSessions`, `engagedSessions`, `intentSessions`, and `actionSessions` are added to existing accepted writes using sessionStorage de-duplication. They must not create a second write path.
- **Category-interest rule:** `viewsByCategory`, `clicksByCategory`, and `categoryNames` are written only when an item view/click is already being recorded.
- **Open-hours action rule:** `actionSessionsByOpenHoursState` and `menuActionClicksByOpenHoursState` are written only on existing final menu action writes. They must not introduce heartbeat, polling, or page-duration tracking.
- **Language-usage rule:** `menuViewsByLanguage` and first-session `menuSessionsByLanguage` are attached to the existing menu-view write. A switched language only writes `languageAdoptions` after it stays active for the dwell window, with `languageNames` stored for dashboard labels.
- **OBP language-usage rule:** OBP uses the same multi-language-only gate. `obpViewsByLanguage` and `obpSessionsByLanguage` are attached to the existing OBP view write; `obpLanguageAdoptions` writes only after the switched OBP language stays active for the dwell window. Single-language OBPs do not track or display language usage. OBP language switch links preserve `entry_source` plus intentional `utm_source`, `utm_medium`, `utm_campaign`, and `utm_content` parameters, and adoption de-dupe is scoped to the store-local analytics day.
- **Attribute-filter rule:** public filter chip selection is kept in `sessionStorage` only. It creates no Firestore write by itself. While the filter remains active, later accepted item/search/unavailable/recommendation/final-action writes attach bounded fields such as `attributeFilterInteractions`, `attributeFilterItemViews`, and `attributeFilterActionClicks`.
- **Source-quality rule:** `entry_source` is the canonical internal source field. `viewsByEntrySource`, `menuSessionsBySource`, `actionSessionsBySource`, and `menuActionClicksBySource` are attached to existing menu view / final action writes. OBP uses the same cost rule with `viewsByEntrySource`, `obpActionClicksBySource`, `obpMenuClicksBySource`, and `obpLinkClicksBySource` attached to existing OBP writes. `viewsBySource`, `viewsByMedium`, `viewsByCampaign`, and `viewsByContent` are UTM campaign fields only and are written only when intentional `utm_*` parameters exist. These fields must not create separate source-tracking writes.
- **External pixel rule:** Google Analytics and Meta Pixel are owner-provided external scripts controlled by the saved IDs in Analytics Settings. Empty IDs mean no script is loaded. These tools may read the public URL and intentional `utm_source`, `utm_medium`, `utm_campaign`, and `utm_content` values on campaign links, but MenuList internal source attribution remains `entry_source`. No extra owner-facing UTM toggle is needed because UTM campaign reporting is link-level behavior, while external script loading is controlled by the GA4 / Meta Pixel ID fields.
- **Owner action rule:** the scheduler writes `sourceQuality`, `ownerConfidence`, item status labels, search-fix actions, and open-hours action breakdowns for all owners from already-collected counters. The Pro analytics assistant layer writes `ownerActionPlan` only when the entitlement check passes.
- **Item status rule:** `Strong item`, `Getting attention`, `Needs work`, and `Unavailable demand` labels are derived during scheduler/DAL aggregation from existing item view/click/recommendation/unavailable maps. Do not add item heatmaps, photo-view tracking, or per-option click tracking for this label.
- **Search-fix rule:** zero-result search recommendations use existing `zeroResultSearchTerms`. Do not add per-keystroke search writes or separate search-suggestion documents.
- **Owner action receipt rule:** owner `Mark done` taps are stored as bounded receipts inside the existing dashboard summary doc. The nightly scheduler preserves those receipts and compares the next settled metrics from the same read model to show `Improved`, `No clear change yet`, or `Not enough data yet`. This loop adds no customer-facing analytics event.
- **Catalog intelligence rule:** Pro menu intelligence joins existing anonymous analytics counters with already-loaded project catalog fields during nightly settlement. It must not create new customer events, raw event docs, or project-doc refetches in the normal scheduler path.
- **Analytics AI entitlement rule:** paid Gemini wording is disabled unless `ENABLE_OWNER_ANALYTICS_AI_SUMMARIES=true` is set for Cloud Functions and `platformSummary/storesSummary.stores.{sId}.activePlanType` is `pro` or `premium`. Missing plan data fails closed and the dashboard read model receives `analyticsAiEntitlement` for the locked desktop/mobile UI state.
- **Billing sync rule:** payment verification, Razorpay webhooks, reseller offline activation, and subscription reconciliation keep `stores/{sId}.activePlanType` and `platformSummary/storesSummary.stores.{sId}.activePlanType` aligned. Only `active` subscriptions set the mirror; `past_due`, `paused`, `cancelled`, `expired`, and `completed` remove it.
- **Analytics AI cost flag:** deterministic read models continue when the flag or plan gate is off. When enabled, this wording uses `gemini-2.5-flash-lite` because the scheduler has already selected the factual metrics/actions.
- **Analytics AI write rule:** when paid summaries are enabled, daily / weekly / monthly Gemini payloads are generated in parallel per project and stored inside the existing `{tId}_{sId}_{projectId}_dashboard_summary` write. They must not create separate summary-only Firestore writes.
- **Storage rule:** all raw tracking metrics must be additive fields on the existing daily analytics doc. Owner dashboards may use nightly read-model docs in the same `analytics` collection to avoid repeated daily-range reads.
- **Dashboard read-model rule:** settled owner-facing Dashboard and recent deep analytics data must be read from `{tId}_{sId}_{projectId}_dashboard_summary`. Do not rebuild settled dashboard cards from daily docs on the owner client.
- **Dashboard parity rule:** desktop and mobile owner Dashboard tabs must render the same menu analytics detail sections from the shared owner-dashboard detail builder. Layout may differ, but the section set and source data must not drift.
- **Dashboard tab rule:** owner Dashboard uses `Today`, `Overview`, `Yesterday`, `This Week`, `This Month`, and `Overall` tabs. `Today` reads only current partial Menu + OBP daily docs; opening any settled tab triggers the cached Menu + OBP read-model reads for that scheduler cycle.
- **Public analytics target gate:** `POST /api/public/analytics/track` validates store-to-tenant ownership, store active/deleted/platform block state, inherited tenant block state, and project activity before preference filtering or Admin SDK writes. The validated target is cached for 300 seconds under `client-stores`, so the tenant read is a cache-miss cost, not a per-event write cost.
- **Public analytics route diagnostics rule:** `POST /api/public/analytics/track` must log unexpected target-validation/write failures through bounded analytics diagnostics with tenant/store/project presence and length metadata, update-field count, date-request presence, and source error name/code/status metadata only. Raw tenant/store/project IDs and raw route/provider exceptions must not be passed to `secureError()`. This changes diagnostics only; public rate limiting, body caps, target validation, preference filtering, date validation, and Admin SDK writes are unchanged.
- **Public navigation tracking diagnostics rule:** public menu and OBP final-action navigation tracking must never block customer navigation. Failed `trackBeforeNavigate()` calls log `public_link_navigation_tracking_failed` with a fixed reason label, target-blank boolean, and bounded href/target presence-length metadata only. This adds no analytics Firestore write beyond the existing attempted tracking event.
- **Public menu state storage diagnostics rule:** public menu filter/category/scroll restore and save failures use bounded `public_menu_state_restore_failed` and `public_menu_state_save_failed` diagnostics with storage-key/filter/category presence-length metadata, category count, scroll value, preview-mode flag, and shared tenant/store/project presence metadata only. Browser storage failures remain fail-open and must not create analytics Firestore writes.
- **Store subdomain block analytics diagnostics rule:** `SUBDOMAIN_MUTATION_BLOCKED` remains fire-and-forget when the post-publish public-link guard blocks a subdomain change, but rejected tracking logs `store_subdomain_block_analytics_signal_failed` with bounded store, tenant, current-subdomain, and attempted-subdomain metadata only. This adds no analytics Firestore write beyond the existing attempted tracking event.
- **External GA property rule:** server-side Google Analytics report routes may only query the GA property configured on the current store, except platform-admin sessions. This prevents one tenant from passing another tenant's property id into the shared GA service account. Authorization failures log bounded route/session metadata, requested-property presence/length, tenant/store presence/length, and allowed-property count only; raw `buildSecurityContext()` output and raw property IDs are not written to security logs.
- **External GA logging rule:** server-side Google Analytics initialization/report/realtime failures are logged through the shared bounded analytics diagnostics helper with stable failure codes, env-presence booleans, bounded property/date context, and source error name/code/status metadata only. Raw provider objects, raw provider exception messages, and raw property/date values are not written through direct console logging or the secure-log message field, and browser responses stay generic at the route boundary.
- **Owner analytics read limiter rule:** legacy authenticated owner analytics read routes share `src/app/api/analytics/readRateLimit.ts`, which applies `DATA_READ` before permission/config/provider/read work and stores only HMAC-hashed owner/tenant/store key material in the provider key. Rate-limited requests perform no analytics Firestore read or Google Analytics provider call.
- **Owner analytics API diagnostics rule:** legacy owner analytics read routes (`/api/analytics`, `/api/analytics/menu`, `/api/analytics/locations`, `/api/analytics/realtime`, and `/api/analytics/roi-metrics`) use the same bounded analytics diagnostics helper. They keep the existing permission checks, GA property guard, GA provider requests, ROI calculation, and generic owner responses, but route failures must log only stable codes plus bounded property/date/user/tenant/day metadata and source error name/code/status metadata.
- **OBP browser diagnostics rule:** OBP view and language-adoption client failures use bounded `secureError()` context with tenant/store/language presence and length only. Raw browser exceptions, session IDs, UTM values, and source parameters must not be direct-console logged. This changes diagnostics only; it does not create another analytics event or Firestore write.
- **Owner analytics DAL diagnostics rule:** owner dashboard aggregate, AI intelligence, summary, and comparison read failures use bounded analytics diagnostics with tenant/store presence and length plus date-range validity/day-count context only. Raw Firestore/provider exceptions and raw tenant/store IDs must not be direct-console logged. This changes diagnostics only; the existing read-model reads still rethrow to the same caller boundaries and no extra Firestore read/write is created.
- **Owner analytics health metric rule:** analytics DAL health metrics must be derived from existing analytics aggregates or real monitoring sources. Do not emit hard-coded API response time, uptime, latency, or status values in owner/platform dashboards.
- **Owner analytics comparison rule:** comparison metrics must be derived from existing analytics aggregates. Do not emit placeholder active-user counts or zero total-message counts when `statistics.totalMessages` is available.
- **Platform chat insights summary rule:** Chat Insights summary cards must use existing chat aggregate data. Knowledge Gaps must not show a placeholder prior-period trend, Response Rate must be derived from `totalFeedback / totalChats`, and analytics job failure banners must not render stored raw error strings directly.
- **Analytics normalization diagnostics rule:** normalized metrics validation failures use bounded analytics diagnostics with metrics/date/tenant/store presence and length plus map/metadata presence flags only. Raw malformed read-model payloads and raw validation exceptions must not be direct-console logged. This changes diagnostics only; invalid normalized metrics still return `false`.
- **Dashboard GA card diagnostics rule:** legacy Google Analytics dashboard cards use bounded analytics diagnostics with property/date presence and length metadata only. Raw GA property IDs, date ranges, response rows, provider errors, and browser exceptions must not be direct-console logged. The shared browser service caps GA response JSON at 1MB, validates report-like response rows, and normalizes `/api/analytics/reports` to the `report` object before cards read `.rows`. Quick Stats and Trend Analysis must read revenue from the `totalRevenue` metric index and must not read an unavailable order metric from the reports route. `DateRangeSelector` persists `analytics.dashboardPreferences.dateRange` through the existing `updateStore()` write and requires acknowledgement before considering that preference saved; persistence failures log bounded analytics diagnostics and do not block the visible dashboard range change. This changes browser response parsing, reports normalization, dashboard metric-index alignment, diagnostics, preference-write acknowledgement, and the zero-total Location Insights percentage guard only; it adds no Firestore read/write beyond the existing preference write and no GA provider request.
- **Owner dashboard cache diagnostics rule:** settled dashboard and Owner Business Assistant SWR/localStorage cache failures use development-only bounded `secureError()` context. Raw cache keys, prefixes, cached read-model values, and browser storage exceptions must not be direct-console logged. This changes diagnostics only; cache fallback behavior and Firestore read-model reads are unchanged.
- **Custom range rule:** do not precompute every possible owner-selected range. Keep one compact rolling daily read model; older/custom ranges outside that window are not fetched from daily docs by default.
- **Intelligence input rule:** Decision Blocks and Menu Intelligence must use `{tId}_{sId}_{projectId}_intelligence_7d`. Missing/stale snapshots return empty for that run; they must not trigger hidden daily-doc reads.
- **Owner-visible rule:** Firestore tracking is reserved for metrics shown in owner dashboards or required by scheduler decisions. Generic ecommerce/auth/share/location/ops events stay GA4-only until they have a real owner-facing read model.
- **Variant/option rule:** item `attributes` are catalog variants/options. They are not tracked as clicks unless they become real selectable customer controls in a future flow.
- **Cache rule:** scheduler-backed owner data is cached by store-local scheduler cycle, not by midnight. It invalidates after the next expected local scheduler completion window; partial `Today so far` data keeps a 10-minute TTL.
- **Business-day rule:** daily analytics docs use `storeTimeZone` + `businessDayEndTime` (`HH:mm`) for the owner-facing date key. The field is stored on both `stores/{sId}` and `platformSummary/storesSummary.stores.{sId}` so the scheduler does not fetch every store doc.
- **Date rule:** daily analytics docs use the **store business-day date** and hourly buckets use the **store timezone**. Analytics no longer rely on UTC day keys for owner-facing menu / OBP / Customer App reporting.
- **Daily metadata rule:** every daily analytics write must include `tId`, `sId`, `projectId`, `grain`, `surface`, `localDate`, and `storeTimeZone` in the same write as the counters. This enables store/date settlement queries without extra event writes.
- **Settlement rule:** nightly aggregation is idempotent. Lifetime totals must never increment when the target local date is already recorded as settled on the summary/state documents.
- **Late-event correction rule:** the next nightly pass checks the previously settled local date against the cached daily row and applies only positive deltas. This catches delayed passive writes without reopening arbitrary historical ranges.
- **Catch-up rule:** if the scheduler misses a night, the next local nightly run processes pending store-local dates in order, capped per run to protect Firebase cost.
- **Index rule:** `firestore.indexes.json` must include the analytics settlement index `analytics: tId ASC, sId ASC, grain ASC, localDate ASC` before production deploy.
- **Observability rule:** log only actionable analytics anomalies to Sentry/Firebase logs: store/date settlement failure, project aggregation failure, late-event correction applied, dashboard/rollup cache rebuild, stale intelligence snapshot, and client queue flush failure. Do not log every public event or every successful counter write.
