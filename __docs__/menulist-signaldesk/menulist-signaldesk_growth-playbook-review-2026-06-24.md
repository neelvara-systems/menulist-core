# MenuList SignalDesk - Growth Playbook Review

**Status:** Adopted as planning doctrine, not a new runtime feature set
**Created:** June 24, 2026
**Scope:** Validate AI-startup and founder-distribution playbooks against MenuList SignalDesk boundaries.

## Executive Verdict

MenuList should not copy generic viral AI-startup launch tactics directly.

The useful lesson from Lovable, Bolt, Gamma, and solo-founder distribution workflows is not "post more" or "automate outbound." The useful lesson is:

```txt
fast first result
-> shareable proof artifact
-> trust channel
-> measured activation
-> repeat inside one narrow pod
```

For MenuList, that translates to:

```txt
restaurant menu problem found
-> MenuList prepares a current menu preview
-> owner reviews and approves
-> live link is placed on two real customer surfaces
-> proof asset is created
-> SignalDesk uses that proof to pick the next target, partner, or content draft
```

This fits the existing SignalDesk north star: activated businesses with a current list live on at least two customer surfaces within seven days.

## Adopted Principles

| Principle | Decision | SignalDesk impact |
| --- | --- | --- |
| Activation beats attention | Adopt | Continue measuring upload, preview, publish, and two-surface activation instead of scraped leads, sends, views, or replies alone. |
| Proof compounds | Adopt | Content Distribution Rail should turn approved MenuList proof into drafts and calendar items, not generic thought-leadership. |
| Trust channels beat broad influencers | Adopt | Trust Partner Rail should favor restaurant consultants, menu/food photographers, local agency operators, and POS/payment freelancers. |
| One narrow pod first | Adopt | Use one market pod, one source policy, one CTA, one proof asset, and one manual/export path before scaling. |
| Demand listening is useful only with source policy | Adopt | High-intent public signals may enter SignalDesk only when source rules, allowed use, retention, and no-auto-reply boundaries are clear. |
| Owner control stays the moat | Adopt | SignalDesk prepares and compresses decisions; the founder approves, pauses, redirects, or posts manually. |

| LinkedIn scraping or auto-connect | Reject | Platform rules and data-rights risk. |

| Provider send because credentials exist | Reject | Connector readiness does not override source policy, suppression, sender readiness, unsubscribe, or approval gates. |

## Recommended First Pod Hypothesis

This is a recommended default, not a founder-approved final decision.

| Field | Recommended default |
| --- | --- |

| Problem | Current menu is hard to open, stale, PDF/image-only, Instagram-only, or not easy to share from QR/WhatsApp/Google/Instagram |
| CTA | One current official menu link for QR, WhatsApp, Google/profile, Instagram, and repeat customers, reviewed by the owner before publishing |
| Channel | Founder email/manual export first; no cold WhatsApp or cold social DMs |
| Batch size | 25-50 candidates, then 10-20 evidence packets, then a smaller approved outreach/export set |
| Pass condition | At least one clean path to upload, preview, approval, publish, and two-surface activation within seven days |
| Stop condition | Weak evidence, unclear contact rights, repeated objections, no uploads/previews, or safety/compliance blocks |

## MenuList-Side Activation Concierge

The strongest missing product slice is not another SignalDesk marketing automation. It is the MenuList-side activation path that receives interested owners and gets them live.

SignalDesk may route to it, watch it, and summarize outcomes. SignalDesk must not own or mutate the MenuList truth.

Required MenuList-side path:

```txt
upload menu photo/PDF/link
-> parse/extract current menu
-> normalize sections/items/prices
-> generate owner preview
-> owner edits/reviews/approves
-> publish customer link
-> generate QR
-> prepare WhatsApp share copy
-> prepare Google/Profile placement checklist
-> prepare Instagram bio/link checklist
-> track two-surface activation
```

This should become the primary next feature doc set after the SignalDesk local trial is clean.

## SignalDesk Automation Priorities

| P0 | High-intent demand listener | Source-policy-gated, no auto-reply, no scraping where platform rules prohibit it. |
| P0 | Proof asset generator | Uses approved MenuList proof only; drafts are approval-gated and never auto-published. |
| P1 | Trust partner autopilot | Discovery, scoring, briefs, deliverables, and renewal recommendations only; no automated contracts or payments. |
| P1 | Objection intelligence | Learn from real replies after the first pod; do not invent pricing conclusions before data exists. |

## First 30-Day Operating Plan

| Period | Goal | SignalDesk role |
| --- | --- | --- |
| Days 1-3 | Lock first pod, source policy, sender identity, physical address policy, unsubscribe/suppression policy, CTA, and proof format. | Show owner decisions and block unsafe runs. |
| Days 4-7 | Run 25-50 candidates through source, dedupe, evidence, draft, approval, export/manual send, reply, route, and outcome capture. | Prove one complete loop with small numbers. |
| Days 8-15 | Build proof from early activations and test 3-5 trust partners. | Queue approval-gated proof drafts and partner briefs. |
| Days 16-30 | Repeat only what converts into uploads, previews, publishes, and two-surface activation. | Recommend continue, narrow, change, or pause. |

## Codebase Decision

No new runtime feature should be added from this review alone.

The current SignalDesk runtime already contains the private workspace, Operating Layer records, offer CTAs, reply playbooks, experiment cards, source-quality snapshots, Content Distribution Rail, Trust Partner Rail, approval gates, sender gates, source-policy expiry, mobile read-only controls, and provider-send disabled posture.

The needed repo change is documentation alignment:

1. record this growth-playbook review;
2. update the action register defaults;
3. make the next implementation slice focus on one pod and MenuList-side activation concierge docs/runtime;
4. keep unsafe automations rejected.
