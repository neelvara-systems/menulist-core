Build `1234895fdd013fa03d59400dcd8253f6d9fd6d0b` restricted webhook lookup to the signed/intended configured product stores; Razorpay automatically retried `subscription.cancelled`, the hosted route returned HTTP 200, and the owner UI converged to `No Active Subscription`. Exact cleanup removed that disposable local subscription, while retained baseline `sub_TPGo1XmddplChB` remained provider `created`, unpaid, and unchanged. A real Razorpay `payment.failed` payload with provider amount `0` also exposed a positive-only revenue projection and order-backed top-up misclassification. Build `2780c22a821719b6c1ee7cf1543f2f45eb17d6be` now accepts zero for failed-payment audit projection, derives a bounded fallback only from an exact persisted subscription, and classifies top-ups only from an explicit pack identity. The current Test webhook is enabled for 13 events, including `subscription.authenticated`. The original failed-payment delivery is still awaiting Razorpay's provider-controlled automatic redelivery; do not represent that single transport retry as certified until a current-build HTTP 200 is observed. Full immediate-start authorization, `subscription.activated`, and captured `subscription.charged` smoke remain externally blocked at the Razorpay Test Checkout/mock-bank boundary. See Razorpay's [subscription test lifecycle](https://razorpay.com/docs/payments/subscriptions/test/?preferred-country=IN), [test-card contract](https://razorpay.com/docs/payments/payments/test-card-details/?preferred-country=IN), [subscription webhooks](https://razorpay.com/docs/webhooks/subscriptions/), and [webhook retry guidance](https://razorpay.com/docs/webhooks/best-practices/).

> **August 13, 2026 lifecycle authority correction:** the authenticated checkout callback remains a required recovery path, but it never trusts browser claims alone: it validates the checkout HMAC, fetches the payment and subscription from Razorpay, and requires the same captured payment/subscription pair before settlement. Signed webhooks own asynchronous lifecycle convergence. All 10 documented subscription webhook events are handled. `subscription.authenticated` and `subscription.activated` both leave the local row `pending`; activation may store bounded provider/cycle metadata and sets `capturedPaymentSyncPending: true`, but it grants no entitlement, money, payment history, MRR, notification, replacement finalization, or credit reset. Only the verified callback or `subscription.charged` with a captured `pay_*` identity bound to the same provider subscription performs recurring payment settlement and can transition local status to entitled `active`. Webhook deduplication prefers Razorpay's `x-razorpay-event-id`; unsafe IDs are hashed rather than character-normalized. Because Razorpay does not guarantee delivery order, a late captured `subscription.charged` can append payment truth to a locally `cancelled`/`completed` row without reopening entitlement, changing terminal provider state, or resetting credits.

> **August 13, 2026 pending-checkout recovery correction:** authenticated owner surfaces never open a pending subscription's persisted Razorpay `shortUrl`. They call `POST /api/razorpay/create-subscription`, which fetches current provider truth. A provider `created` row without an in-progress eMandate reopens Standard Checkout for the same subscription. A `created` eMandate remains `processing` for 48 hours because Razorpay confirmation can be asynchronous; no second checkout, entitlement, ledger entry, MRR, notification, or credit reset is created. After that window, a user-triggered retry must cancel and prove the old provider subscription terminal before transactionally expiring the local pending row and creating one replacement. Past-due recovery and unauthenticated reseller handoff continue to use Razorpay's hosted payment link as separate provider-owned workflows.

## Key Architecture Facts

- **Payment provider:** Razorpay only (Stripe removed Feb 2026)
- **Subscription documents:** Root-level `subscriptions/{subscriptionId}` rows carry exact tenant/store aliases. A store can own a direct subscription; a MenuList outlet without one can inherit its tenant master/HQ subscription for access and shared enhancement balance.
- **Owner mutation scope:** The desktop/mobile store picker is a read context. Plan changes, recurring payment links, quantity changes, and direct subscription actions are enabled only for the signed-in store's direct subscription; switched-store views are read-only. An inherited outlet can buy an enhancement pack into the shared HQ balance but cannot mutate the HQ plan.
- **Provider boundary:** `billingMode: 'manual'` and `manual_...` prepaid subscriptions never call Razorpay subscription APIs. Reseller renewals and prepaid location capacity are separate server-owned, idempotent Firestore flows.
- **Pending data shape:** every online creation path persists local `status: 'pending'` with provider `providerStatus: 'created'`, null billing-cycle dates, `billingHistory: []`, and no active entitlement. Authentication stays pending. Activation stores `providerStatus: 'active'`, bounded cycle metadata, and `capturedPaymentSyncPending: true` while local status remains pending. Captured settlement appends the exact `pay_*` identity, updates the paid count/cycle, clears the marker, and only then makes local status `active`. A legacy local `active` row without captured-payment evidence is projected as payment-pending and is included in the unresolved-checkout lookup, so a retry checks the existing provider subscription instead of creating a duplicate.
- **Provider-call scalar boundary:** shared Razorpay subscription fetch/quantity helpers accept only exact `sub_...` IDs and positive safe-integer quantities within the existing 31-location limit. Persisted IDs are not scalar/object-coerced, malformed input fails before provider client import, and throwing provider error objects cannot break the recovery classifier.
- **Credit types:** Monthly (resets each billing cycle) + Top-up (never expires)
- **Reset mechanism:** Two-layer — captured `subscription.charged` settlement (monthly plans) + lazy reset in capacity check (yearly + safety net). Authentication and activation alone never reset credits.
- **Grace period:** 7 days for failed payments, enforced in DAL (`expireIfGracePeriodEnded`). Server entitlement reads also require captured-payment evidence before returning active/cancelled/paused/past-due access.
- **Grace display fallback:** Desktop Billing, Mobile Billing, and authenticated pricing subscription-management use the shared past-due grace-period display fallback. If a legacy or malformed `past_due` doc is missing `pastDueSinceAt`, owner UI shows fixed "Grace period details unavailable." recovery copy instead of a false zero-day countdown.
- **Top-ups:** One-time Razorpay Orders (not Subscriptions). Either the authenticated checkout callback or the signed `order.paid` webhook can settle the immutable pending top-up snapshot; the Firestore transaction applies credits exactly once.
- **Billing history:** Sourced from webhook event log (`paymentTransactions` collection, append-only lean v2 summaries)
- **Billing-resource isolation:** Browser and Admin subscription/history queries, billing mutation transactions, scheduled reconciliation/expiry/messaging/AI recovery, and Firestore subscription/top-up/transaction rules require both exact product aliases. A guarded collection-selected dry-run migration completes the second MenuList alias only where legacy rows already prove `pId: ML`; alias-less, conflicting, or other-product rows remain quarantined.
- **Payment action body caps:** Authenticated subscription, top-up, verification, upgrade, pause/resume, cancel, and onboarding billing JSON routes use bounded request parsing before Zod validation, provider calls, or Firestore writes.
- **Answerlattice billing permission:** Shared Razorpay mutations re-read the current Answerlattice workspace membership and persisted role and require `canManageBilling`; general management access alone does not authorize payment changes.
- **Document-ID boundary:** Subscription document refs pass through `src/lib/billing/subscriptionDocumentIdBoundary.ts` before DAL, AI capacity, entitlement sync, and top-up verification refs.
- **Top-up order document-ID boundary:** Raw top-up order refs pass through `src/lib/billing/topupDocumentIdBoundary.ts` before pending writes, idempotency reads, and paid audit writes; whitespace-mutated order IDs fail before Firestore refs.
- **Top-up subscription settlement boundary:** Verification proves a currently entitled subscription with captured-payment evidence exists before provider capture, then re-reads the exact document in the credit transaction. Missing, unpaid-provider-active, re-scoped, conflicting-product, or malformed-balance current documents fail closed without recreation or stale balance fallback.
- **Webhook cheap-fail:** Missing signature/secret, signatures outside the exact 64-character lowercase HMAC-SHA256 hex shape, oversized bodies above 256KB, and IP-rate-limited bursts are rejected before raw-body digest comparison or Firestore idempotency work. Valid signatures retain timing-safe comparison against the raw request body.
- **Webhook idempotency:** Signed webhook events are claimed in server-only `razorpayWebhookEvents/{eventKey}` before billing mutations. The canonical `x-razorpay-event-id` header is preferred and a valid envelope ID is the compatibility fallback. A malformed/oversized canonical header is rejected; a bounded identity containing Firestore-unsafe characters is represented by a SHA-256 document key so distinct provider identities cannot collide through character replacement. Processed replays return a successful duplicate acknowledgement only when the persisted row has the exact version, embedded event identity, attempt, timestamp, retry and provider-metadata contract; malformed Admin/legacy state fails retryably instead of suppressing payment work. A concurrent active attempt returns retryable `503` instead of falsely telling Razorpay the event is complete. Every terminal write is attempt-fenced, deterministic payment/failure alerts and lifecycle references cannot duplicate on recovery, and a stale worker cannot downgrade a newer successful retry.
- **Webhook product recovery:** When a subscription payment event omits product notes, the handler resolves the provider subscription against MenuList and Answerlattice billing stores before audit, alert, or state mutation.
- **Replacement subscriptions:** Upgrade/create requests persist `replacementForSubscriptionId`. Server-verified browser settlement or a captured matching `subscription.charged` webhook can finalize the replacement; authentication/activation alone cannot. Finalization cancels the old provider subscription before the idempotent two-document carry-forward transaction and safely resumes after a partial failure. A late charge may finalize a terminal replacement only when that exact `pay_...` ID was appended by the captured-payment transaction.
- **Creation recovery:** Existing-user, website-onboarding, reseller-online, and Answerlattice onboarding creators check ambiguous persistence outcomes and compensate provider/local provisioning only when safe. Sequential retry reuses a matching provider `created` subscription instead of creating another checkout.
- **Concurrent checkout recovery:** Existing-user subscription and top-up creation acquire a short server-only scope lease, then transactionally change it from `processing` to `provider_creating` immediately before the provider call. Only a version-2 expired `processing` lease is safe to renew or release because that version proves no provider side effect began; unversioned rolling-release leases fail into provider recovery. An expired `provider_creating` subscription is recovery-only: the route searches by the exact `checkoutAttemptId` and returns `409` while the result remains ambiguous instead of creating a second subscription. Top-up orders may retry the same attempt because their 36-character attempt-derived Razorpay `receipt` stays below the documented 40-character limit and is unique; the retry first searches that receipt and never changes it. ([Razorpay order creation contract](https://razorpay.com/docs/api/orders/create/), [subscription creation contract](https://razorpay.com/docs/api/payments/subscriptions/create-subscription/)) After provider creation, the lease records one exact immutable provider ID. That checkpoint can be released only after explicit compensation of the matching subscription; fetch/shape/recovery errors retain it. After local persistence a two-minute checkpoint replays the entity so an already-running request cannot create another object.
- **Plan lookup:** Razorpay plan deduplication uses the server-only `billingProviderPlans` Firestore registry plus complete bounded provider pagination. Its versioned state machine transactionally distinguishes pre-provider `processing` from possibly-effectful `provider_creating`. An expired pre-provider owner may be replaced; an expired provider-started or unversioned rolling-release attempt may only search/recover the canonical `lookupKey` and cannot create another plan while unresolved. Concurrent requests wait briefly, one exact provider ID becomes durable `ready` truth, and malformed/product-conflicting rows fail closed.
- **State machine:** All status transitions are validated by `subscriptionStateMachine.ts`; invalid transitions are blocked before status writes, and transition introspection returns a copy so callers cannot mutate the shared transition table.
- **DAL architecture:** 3-layer composition — `fetchSubscriptionRaw` → `expireIfGracePeriodEnded` → `getActiveSubscriptionForStore`. The client path keeps pending rows visible for checkout recovery; the server entitlement path fails closed unless payment evidence is verified.
- **Reconciliation authority:** provider lifecycle status can repair non-monetary state, but provider `active`/`paid_count` alone cannot create a local payment ledger, reset credits, or grant access. Reconciliation promotes to active or advances cycle dates only when the local exact `pay_*` ledger count already matches provider `paid_count`; otherwise it preserves local status and sets `capturedPaymentSyncPending: true` for observable webhook/callback recovery.
- **Bounded history:** New subscription status entries retain the latest 100 diagnostic entries. Payment settlement identifiers remain in the separate idempotency ledger and are not truncated.
- **Subscription lifecycle policy:** The shared byte-identical app/Functions policy admits the 10 official subscription events, exact expected event/status pairs, and all 9 provider states. Every admitted subscription event requires a bounded subscription entity before the event claim. A charged event additionally requires a bounded payment ID, `captured` status, and matching `payment.subscription_id`. The local status intentionally stays compact: provider `created`/`authenticated` remain `pending`; provider `pending`/`halted` map to `past_due`; `subscription.updated` records provider state even when no quantity field is present.
- **Reconciliation:** The leased 2:20 AM UTC task processes exact-dual-`ML` `pending`/`active`/`past_due`/`paused` subscription pages of 100 rows with five provider calls at a time, a six-minute runtime budget, and a Firestore cursor. It revalidates product identity in each transaction and syncs all provider states, cycle, charge, paid-count, and quantity truth without loading the whole population into memory.
- **Paid-cycle plan entitlement:** Current `active`, `cancelled`, and `paused` subscriptions carry the purchased plan mirror only when captured/manual payment evidence exists and `cycleEndDate` is exact and has not elapsed, matching the owner-visible paid-access promise and the transaction query. Missing, malformed, or elapsed payment/cycle evidence and `past_due`, `expired`, or `completed` status fail closed. Browser/Admin timestamp shapes are read without method invocation or scalar coercion, and plan IDs must be bounded strings. Legacy/provider rows missing payment or cycle evidence require provider reconciliation rather than implicit entitlement. The existing maintenance scheduler queries only exact-dual-`ML` rows, checks at most 500 due cancelled/paused rows each hour, revalidates product identity before mutation, transitions them to `expired`, synchronizes store/platform mirrors, and leaves a durable retry marker if the post-transition entitlement repair fails.
- **Billing health and retention:** The existing maintenance scheduler exact-replaces one daily server-only `systemHealth/billing` summary for stale pre-provider/provider-ambiguous checkout and provider-plan work, orphaned provider-created checkouts, failed webhooks, and expired webhook claims. Provider ambiguity is critical attention through the existing cooldown-aware platform alert path. Terminal or stale-processing webhook idempotency claims older than 90 days are deleted in batches of at most 200; checkout/plan recovery state and all recent webhook claims are preserved.
- **Architecture status:** FROZEN — only new plans, price changes, credit packs allowed; no structural changes
