## Rule 1 — Product Evolution Sequence (LOCKED)

MenuList follows **one** evolution path. No parallel products. No fragmentation.

```
🥇 STAGE 0: MenuList Dominance (NOW → ongoing)
    Menu truth + hours truth + presence + correctness + mobile
    This stage NEVER ends. MenuList is always priority #1.
    
    ↓ (only when MenuList is stable, trusted, daily dependency)

🥈 STAGE 1: Control Layer INSIDE MenuList
    MenuList evolves from "menu infrastructure" to "business truth infrastructure"
    NOT a separate product. NOT a new brand.
    Expands: business identity, public notices, presence consistency
    
    ↓ (only when MenuList becomes system-of-record)

🥉 STAGE 2: GrowthOS (Revenue Execution Engine)
    Promotion + demand generation on TOP of trusted truth layer
    Only works because authority already established
    
    ↓ (optional, only if organic demand)

4️⃣ STAGE 3: KitStamp (Premium Content Workspace)
    Optional forever. Never allowed to distract from core.
```

### Enforcement Rules

- **NEVER** start a later stage before the current stage is solid
- **NEVER** build GrowthOS before MenuList is system-of-record for SMB public presence
- **NEVER** launch ControlOS as separate product/brand/dashboard
- **NEVER** let KitStamp distract from MenuList focus
- If any idea breaks this order → **REJECT immediately**

## Rule 2 — Customer-Facing Only Boundary (PERMANENT)

MenuList exists in **one layer only**: the customer-facing layer.

### What MenuList Owns (Customer-Facing Layer)

Everything customers see or experience:

- **Menu** — items, prices, descriptions, availability, categories
- **Hours** — open/closed, special hours, closures, holiday timing
- **Business identity** — name, logo, phone, address, service modes
- **Public presence** — OBP, QR, screens, Google, official link
- **Public communication** — temporary notices, closures, announcements
- **Reputation** — reviews, feedback, rating protection
- **Discovery** — recommendations, highlights, decision blocks
- **Consistency** — same truth everywhere customers look

### What MenuList NEVER Builds (Internal Operations Layer)

These are permanently rejected. No exceptions. No "just a small version."

| Rejected Category | Why |
|-------------------|-----|
| ❌ POS / billing / payments processing | Internal operations |
| ❌ CRM / customer database | Internal operations |
| ❌ Inventory / stock management | Internal operations |
| ❌ Payroll / HR / employee management | Internal operations |
| ❌ Accounting / finance tools | Internal operations |
| ❌ Loyalty programs / gamification | Wrong product category |
| ❌ WhatsApp marketing campaigns | Marketing tool territory |
| ❌ Order management / kitchen display | POS territory |
| ❌ Booking / reservation engine | Booking tool territory |
| ❌ Staff management / surveillance | Creates wrong incentives |

### The Filter

> **If a feature does NOT affect what customers see or experience → it does NOT belong in MenuList.**

## Rule 3 — The 5-Minute Understanding Rule

> **If a non-tech SMB owner cannot understand MenuList's purpose and basic usage within 5 minutes — without training, without a manual, without explanation — we have failed.**

### What "5-minute understanding" means

Within first 5 minutes, owner must grasp:

1. **Minute 0-1:** "This controls my menu and business info"
2. **Minute 1-3:** Upload menu, see preview, set hours
3. **Minute 3-5:** Approve a change → see the supported customer link and connected MenuList outputs refresh

### The Test

- **PASS:** Owner says "I approve it once, then my MenuList customer links and outputs use it"
- **FAIL:** Owner asks "What does this do?" or "Where do I click?"

### Implications

- If owner needs training → **feature is too complex**
- If owner needs a manual → **UI is too complex**
- If owner needs thinking → **system is too complex**
- Every new feature must pass: "Will this make the product harder to understand in 5 minutes?"

## Rule 5 — Silent Autopilot Design Principle

> **Every feature in MenuList must behave like a silent autopilot system.**

### What This Means

- Owner does NOT "manage channels" — they update core truth once
- Owner does NOT "push updates" — system propagates automatically
- Owner does NOT "configure sync" — consistency is default
- Owner does NOT "check dashboards" — system runs without attention

### Design Rules

1. **Single source of truth** — Only one canonical value exists. No duplicates.
2. **Silent propagation** — Owner updates once. System handles the rest.
3. **No dashboard addiction** — This is not an engagement analytics product. Keep approval, correction, billing, and settled health views compact.
4. **High trust system** — Public output comes from owner-approved truth, uses conservative fallbacks, and shows less rather than inventing certainty.
5. **Customer-facing only** — Everything must affect what customer sees.

### When UI Appears

UI should appear only when human confirmation is genuinely required:

- "Today is marked closed but screens are scheduled. Keep closed everywhere?" → One tap confirm.
- NOT: engagement dashboards, routine monitoring screens, or status panels that ask the owner to supervise healthy operation.

## Rule 6 — What MenuList Must NEVER Become

### The Warning Signs

If any of these appear, system is drifting:

- [ ] UI getting crowded
- [ ] Rising support tickets about complexity
- [ ] Too many settings pages
- [ ] Customers using only partial features
- [ ] Frequent bug fixes from feature interactions
- [ ] Confusion about product purpose
- [ ] Requests for internal operations tools becoming frequent
- [ ] "Just one small feature" additions accumulating

### The Kill-Switch

If any addition:
- Complicates the system → **pause or remove**
- Increases support burden → **pause or remove**
- Weakens authority positioning → **pause or remove**
- Blurs product identity → **pause or remove**

Even after release if necessary. Long-term clarity > short-term convenience.
