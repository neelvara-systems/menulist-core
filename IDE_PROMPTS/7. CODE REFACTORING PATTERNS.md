## 📋 WHEN TO USE THIS PROMPT

Use these patterns when:
- Reviewing existing code for improvements
- Identifying and eliminating redundancy
- Consolidating related constants/types
- Cleaning up after feature implementation

## 🎯 PATTERN 1: Redundancy Elimination

### The Problem

```
When related data exists in multiple places, you have to:
- Update multiple files for one logical change
- Keep duplicates in sync
- Risk inconsistencies
```

### The Solution: Single Source of Truth

```
BEFORE (Redundant):
├── constants.ts          # FEATURE_FRIENDLY_INFO = { icon, name, desc }
└── types.ts              # FeatureType = { id, label, prompt }

AFTER (Consolidated):
└── types.ts              # FeatureType = { id, label, prompt, icon, name, desc }
```

### Detection Checklist

```
□ Same entity described in multiple files?
□ Adding a new item requires updating 2+ places?
□ Lookup tables that map to existing type properties?
□ "Info" or "Meta" objects that extend existing types?
```

### Implementation Steps

```
1. Identify the PRIMARY data structure (usually the type/interface)
2. Extend the type to include ALL related fields
3. Update the data array to include new fields
4. Update consumers to use extended type directly
5. Delete the redundant file/constant
6. Update imports in all dependent files
```

## 🎯 PATTERN 2: Type Extension for Display Info

### The Problem

```typescript
// Type has technical fields
type Feature = { id: string; prompt: string; }

// Separate lookup for display info
const DISPLAY_INFO = { 
  'feature-1': { icon: 'X', label: 'Nice Name' } 
}

// Component has to do lookup
const info = DISPLAY_INFO[feature.id]; // Extra step, potential undefined
```

### The Solution: Extended Type

```typescript
// Type includes ALL fields
type Feature = { 
  id: string; 
  prompt: string;
  // Display info directly on type
  icon?: string;
  label?: string;
  description?: string;
}

// Component uses directly
<span>{feature.label}</span> // No lookup needed
```

### Benefits

```
✅ No lookup logic needed in components
✅ Type safety for display fields
✅ Single source of truth
✅ IDE autocomplete for all fields
✅ Adding new feature = one place only
```

## 🎯 PATTERN 3: Icon String Mapping

### When to Use

When storing icon references in data files (JSON-like structures), use string names instead of React elements.

### The Pattern

```typescript
// DATA LAYER (imageViewType.ts)
const FEATURES = [
  { 
    name: "Enhance",
    icon: "LuZap",  // String name, not React element
  }
];

// COMPONENT LAYER (Component.tsx)
import { LuZap, LuPalette, LuScissors } from 'react-icons/lu';

const ICON_MAP: Record<string, React.ReactNode> = {
  'LuZap': <LuZap />,
  'LuPalette': <LuPalette />,
  'LuScissors': <LuScissors />,
};

// Usage
const icon = feature.icon ? ICON_MAP[feature.icon] : <DefaultIcon />;
```

### Why This Pattern

```
✅ Data layer stays serializable (no React imports)
✅ Icons can be stored in JSON/DB
✅ Component controls rendering
✅ Fallback handling in one place
✅ Easy to add new icons to mapping
```

## 🎯 PATTERN 4: Constants Consolidation

### When to Consolidate

```
CONSOLIDATE when constants are:
- Only used by one feature
- Closely related to a type definition
- Small enough to not bloat the file

KEEP SEPARATE when constants are:
- Used across multiple unrelated features
- Large datasets (1000+ lines)
- Shared utilities (like DB_COLLECTIONS)
```

### File Organization

```
GOOD: Feature-scoped constants with their types
├── imageViewType.ts
│   ├── ImageEditingFeatureType (type)
│   ├── PLATFORM_EDITING_FEATURES (data)
│   ├── BUSINESS_FEATURE_MAP (config)
│   └── UNIVERSAL_FEATURES (config)

BAD: Separate file for 2-3 small constants
├── imageViewType.ts (type + main data)
├── constants.ts (2 small exports) ← DELETE, consolidate above
```

## 🔄 REFACTORING WORKFLOW

### Step 1: Identify Redundancy

```
□ List all files related to the feature
□ Identify data that describes same entity
□ Check if adding new item requires multiple updates
□ Document the redundancy
```

### Step 2: Plan Consolidation

```
□ Decide on single source of truth location
□ Extend types if needed
□ Plan import updates
□ Identify files to delete
```

### Step 3: Execute

```
□ Extend type with new fields
□ Update data with new field values
□ Update component to use extended type
□ Update imports
□ Delete redundant file
□ Test that nothing broke
```

### Step 4: Document

```
□ Update verification.md with changes
□ Update README.md version history
□ Note pattern used for future reference
```

## ⚠️ ANTI-PATTERNS TO AVOID

### ❌ Over-Separation

```
BAD: Creating new file for 1-2 constants
BAD: Separate "types" and "data" files for same entity
BAD: Lookup tables when type extension works
```

### ❌ Under-Separation

```
BAD: 10,000 line file with unrelated types
BAD: Constants from different features in one file
BAD: Mixing business logic with type definitions
```

### ❌ Premature Abstraction

```
BAD: Creating generic patterns for one-time use
BAD: Building "framework" before second use case exists
GOOD: Wait for pattern to emerge from 2+ real cases
```

## 📝 EXAMPLE: AI Image Generation Refactor

### Before (Redundant)

```
constants.ts:
├── FEATURE_FRIENDLY_INFO (60 lines)
├── BUSINESS_FEATURE_MAP (8 lines)
└── UNIVERSAL_FEATURES (1 line)

imageViewType.ts:
├── ImageEditingFeatureType (5 fields)
└── PLATFORM_EDITING_FEATURES (same features, different fields)
```

### After (Consolidated)

```
imageViewType.ts:
├── ImageEditingFeatureType (9 fields - extended)
├── PLATFORM_EDITING_FEATURES (includes friendly info)
├── BUSINESS_FEATURE_MAP (moved from constants.ts)
└── UNIVERSAL_FEATURES (moved from constants.ts)

constants.ts: DELETED
```

### Result

```
✅ Adding new feature = 1 place (PLATFORM_EDITING_FEATURES)
✅ No lookup logic in EditImageModal.tsx
✅ Type safety for all display fields
✅ 1 less file to maintain
```

## 🔑 KEY PRINCIPLES

1. **Single Source of Truth** > Convenient separation
2. **Type Extension** > Lookup tables
3. **String Icon Names** > React elements in data
4. **Consolidate Related** > Separate Everything
5. **Delete After Moving** > Leave empty files
