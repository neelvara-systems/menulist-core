# 📚 DOCUMENTATION STRUCTURE & ORGANIZATION PROMPT

**Purpose:** Establish consistent structure for feature documentation that serves multiple audiences.
**When to Use:** After feature is complete, for documentation cleanup, or when creating new feature docs.

---

## CORE PRINCIPLES

### 1. Multi-Audience Documentation

Every feature documentation must serve these audiences:

| Audience               | Primary Document | What They Need                                            |
| ---------------------- | ---------------- | --------------------------------------------------------- |
| **CEO / PM / Clients** | `_spec.md`       | Business value, user flows, scope (no jargon)             |
| **Developers**         | `_impl.md`       | Technical blueprint, DB schema, API contracts, file paths |
| **Sales / Marketing**  | `_marketing.md`  | Pitch deck, landing page copy, messaging                  |
| **QA / Testing**       | `_test-cases.md` | Test scenarios, edge cases, QA matrix                     |
| **Public Docs Site**   | `README.md`      | Index, navigation, quick reference                        |

### 2. Single Source of Truth

```
__docs__/[feature-name]/
├── README.md                           # Index + Navigation (all audiences)
├── [feature-name]_spec.md              # Business requirements (non-tech)
├── [feature-name]_impl.md              # Technical blueprint (developers)
├── [feature-name]_marketing.md         # Sales/Marketing collateral
├── [feature-name]_test-cases.md        # QA matrix (if applicable)
├── [feature-name]_[subfeature].md      # Additional technical docs (if needed)
└── _archive/                           # Historical/audit files (not deleted)
```

### 3. Special Folders

| Folder                        | Purpose                                                     | When to Update                                     |
| ----------------------------- | ----------------------------------------------------------- | -------------------------------------------------- |
| `__docs__/internal-platform/` | **INTERNAL ONLY** - Platform admin features, internal tools | Adding new platform screens, roles, internal tools |
| `__docs__/roles-permissions/` | Customer RBAC system                                        | Adding permissions, changing role structure        |
| `__docs__/auth-onboarding/`   | Auth flows, signup, payment                                 | Changing auth/onboarding flows                     |

**IMPORTANT:** `internal-platform/` is for MenuList.ai team features ONLY - never share with customers.

### 3. Naming Convention (MANDATORY — 3-YEAR FREEZE RULE)

```
ALL file names MUST follow these rules with ZERO exceptions:

1. ALL LOWERCASE — no uppercase letters ever
2. WORDS SEPARATED BY HYPHENS (-) — no spaces, no underscores in names
3. SINGLE UNDERSCORE (_) separates feature-name from doc-type ONLY
4. Feature prefix MUST match folder name exactly
5. Standalone files (no doc-type): all-lowercase-kebab-case.md
6. README.md is the ONLY exception (universal convention)

Pattern: {feature-name}_{doc-type}.md

✅ CORRECT:
__docs__/multi-outlet-consistency/multi-outlet-consistency_spec.md
__docs__/gbp-sync/gbp-sync_doc-feedback-audit.md
__docs__/strategy/pricing-strategy.md (standalone, no doc-type)

❌ WRONG:
__docs__/multi-outlet-consistency/spec.md (missing feature prefix)
__docs__/multi-outlet-consistency/SPEC.md (uppercase)
__docs__/gbp-sync/GBP_SYNC_spec.md (uppercase, wrong separators)
__docs__/strategy/PRICING_STRATEGY.md (uppercase, underscores)
__docs__/strategy/Executive Strategy Doc.md (uppercase, spaces)
```

## DOCUMENT TYPES

### _spec.md (Business/Product)

**Audience:** CEO, PM, Clients, Non-developers
**Tone:** Clear, jargon-free, business-focused

Required sections:
- Executive Summary (what, why, for whom)
- Goals & Success Metrics
- Target Customers (ICP)
- Scope (In-Scope / Out-of-Scope)
- User Stories & Flows
- Requirements (functional, non-functional)
- Risks & Open Questions

### _impl.md (Technical)

**Audience:** Developers, future maintainers
**Tone:** Technical, precise, with code examples

Required sections:
- Architecture Overview
- Database Schema (Firestore structure)
- API Contracts (with Zod schemas)
- File Inventory (exact paths, LOC)
- Security Checklist
- Implementation Patterns
- Testing Guide

### _marketing.md (Sales/Marketing)

**Audience:** Sales team, marketing, landing page writers
**Tone:** Persuasive but honest, customer-focused

Required sections:
- Elevator Pitch (30-second hook)
- Feature Narrative (business value)
- Pitch Deck Outline (7-10 slides)
- Landing Page Copy Hooks
- Sales Talking Points
- Approved Language (refer to Language Governance)

### _test-cases.md (QA)

**Audience:** QA team, developers
**Tone:** Precise, testable, with expected outcomes

Required sections:
- Test Scenarios (with status: ✅/⚠️/❌)
- QA Matrix (table format)
- Edge Cases
- Implementation Coverage Summary

## ARCHIVE FOLDER RULES

### When to Archive (not delete):

- Session logs (CASCADE-FULL-SESSION-*.md)
- ChatGPT review files (*-CHATGPT-*.md)
- Feedback audit files (*_feedback_audit.md)
- Validation reports (*_validation.md)
- Roadmap files (*_roadmap.md)
- Superseded documentation

### Archive Folder Structure:

```

\_archive/
├── [original-filename].md
└── ...

```

### Why Archive Instead of Delete:

1. Historical context for debugging decisions
2. Audit trail for compliance
3. Reference for similar future features
4. ChatGPT conversations contain valuable context

## PUBLIC DOCUMENTATION CONSIDERATIONS

Documents may be published to:
- Client-facing documentation site
- Sales/marketing materials
- Landing page content
- API documentation

**Before Publishing:**

1. Remove internal jargon
2. Remove code paths (keep high-level only)
3. Verify claims match production behavior
4. Apply Language Governance rules (no forbidden phrases)
5. Add appropriate disclaimers

---

## LANGUAGE GOVERNANCE REFERENCE

When writing for public audiences, follow the Language Governance rules:

**FORBIDDEN in public docs:**
- "Smart", "AI-powered", "Dynamic" → Use "Automatic", "Handled"
- "You should", "Consider" → Use "This is handled"
- "Helps you", "Assists" → Use "Manages", "Runs"

**CANONICAL phrases:**
- "No action needed."
- "Everything is running normally."
- "Handled automatically."

See: `__docs__/5YEAR-VISION-2026-COMPLETE.md` (Language Governance Appendix)

---

## EXECUTION

1. Analyze current folder structure
2. Identify audience needs
3. Create README.md first
4. Consolidate scattered files
5. Move audit files to `_archive/`
6. Update cross-references
7. Verify each doc serves its audience

**Quality Check:**
- Can a new developer find technical docs in 30 seconds?
- Can CEO understand the feature without technical details?
- Can sales team find pitch materials easily?
- Are all test cases documented for QA?
