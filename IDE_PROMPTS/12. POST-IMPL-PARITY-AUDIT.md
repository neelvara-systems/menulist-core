# Post-Implementation Parity Audit

**When to run:** After EVERY feature implementation session, BEFORE testing. Non-negotiable.
**Slash command:** `/parity-audit`
**Time:** 15-30 minutes per feature

## Why This Exists

> **Root Cause (Feb 18, 2026 — Messaging Onboarding):** After 3 rounds of file-by-file validation reviews, 14 spec-vs-code mismatches were still undiscovered. The problem: file-by-file reviews verify "does this file look correct internally?" but miss "does the FULL SYSTEM match the FULL SPEC?" Cross-cutting concerns (state machine rules, forbidden transitions, message templates, publish pipeline fields, shared constants) span multiple files and can only be caught by comparing TWO COMPLETE MAPS — one from docs, one from code.

## The Core Problem With File-by-File Reviews

| Review Style | What It Checks | What It Misses |
|-------------|---------------|---------------|
| File-by-file | "Does constants.ts have the right values?" | "Does approve/route.ts use constants.ts or its own inline copy?" |
| File-by-file | "Does sessionEngine.ts handle all states?" | "Does the TERMINAL_STATES array match what spec calls terminal?" |
| File-by-file | "Does the forbidden transitions array look reasonable?" | "Are these the SAME 6 rules the spec defines, or a DIFFERENT set of 6?" |
| **Parity audit** | **"Spec says 6 forbidden transitions with specific from→to pairs. Code has 6 entries. Are they the SAME 6?"** | Nothing — this is the gold standard |

## Methodology: Build Two Maps, Then Diff

### MAP 1: Expected System (from docs only)

Read `_spec.md` and `_impl.md` cover to cover. For each of these 10 areas, write down EXACTLY what docs say:

**A. State Machine**
- List every state name
- List which states are terminal
- List every forbidden transition (from → to → reason)
- List every allowed transition

**B. Constants & Limits**
- Every numeric limit (sessions/day, max uploads, timeouts)
- Every timing value (intake window, fast start, expiry)
- Every threshold (full resend, min categories for publish)

**C. Message Templates**
- Every message text (exact wording)
- Every trigger condition (when is each sent)
- Count total templates

**D. API Contracts**
- Every endpoint (method, path, Zod schema fields)
- Every response shape

**E. DB Schema**
- Every collection name
- Every field in every document type (name, type, default, nullable)

**F. Publish Pipeline**
- Every document created (collection, exact fields)
- Every helper function called
- Every counter updated
- Every post-publish action (messages, OBP, QR)

**G. Security**
- Token generation method + length
- Signature verification method
- Rate limit enforcement points
- Firestore security rules

**H. Integration Points**
- Every existing function reused (exact import path)
- Every existing pattern followed (atomic transaction, summary sync)

**I. Feature Flags**
- Every flag name, default value, location

**J. Error Handling**
- Every failure scenario from spec
- Expected system response for each
- Expected state transition for each

### MAP 2: Actual System (from code only)

Read EVERY implementation file. For each file, extract the same 10 areas.

### THE DIFF

For each area A-J, compare Map 1 vs Map 2 item by item. Classify every difference:

| Classification | Definition | Action |
|---------------|-----------|--------|
| **MISMATCH** | Spec says X, code does Y — direct contradiction | Fix code to match spec |
| **MISSING** | Spec requires X, code doesn't implement it | Implement it |
| **EXTRA** | Code has X, spec doesn't mention it | Remove or document |
| **DRIFT** | Code roughly matches but text/values differ | Fix to exact match |
| **DUPLICATE** | Same logic in 2+ places with different values | Consolidate |

## Fix Priority Order

1. **State machine integrity** (terminal states, forbidden transitions) — breaks routing
2. **Security gaps** (missing token validation, wrong dedup) — breaks safety
3. **Missing post-actions** (no confirmation message, no OBP) — breaks user experience
4. **Logic drift** (wrong message text, wrong threshold) — breaks spec compliance
5. **Duplicates** (inline maps vs shared constants) — breaks maintainability

## Deliverable

After fixing all issues, update `__docs__/[feature-name]/[feature-name]_validation.md`:

```
## Parity Audit — [Date]

### Summary
- Total findings: X
- MISMATCH: X (all fixed)
- MISSING: X (all fixed)
- EXTRA: X (resolved)
- DRIFT: X (all fixed)
- DUPLICATE: X (consolidated)

### Findings & Fixes
| # | Area | Classification | Finding | Fix | File |
|---|------|---------------|---------|-----|------|
| 1 | A | MISMATCH | COOLDOWN not in TERMINAL_STATES | Added to array | types.ts |
...

### Final Verdict: PASS / FAIL
```

## Anti-Patterns This Catches (Real Examples)

| # | Anti-Pattern | Real Example Found | Root Cause |
|---|-------------|-------------------|-----------|
| 1 | Partial forbidden list | Spec: 6 rules. Code: 6 DIFFERENT rules | Each reviewed in isolation |
| 2 | Inline duplication | constants.ts: 17 countries. approve/route.ts: 5 countries | File works alone |
| 3 | Wrong field in array | `providerMediaId` in message dedup instead of `providerMessageId` | Name looks plausible |
| 4 | Missing terminal state | COOLDOWN not in TERMINAL_STATES | Array looks valid with 2 items |
| 5 | Missing post-action | No WhatsApp confirmation after publish | Publish code works internally |
| 6 | Hardcoded vs shared | Inline roles instead of createDefaultRoles() | Roles work, just diverge |
| 7 | Publish validation gap | Constants define min thresholds, no code checks them | Constants exist, unused |

## When NOT To Use This

- During initial implementation (use `4. IMPLEMENTATION PROMPT.md` instead)
- For doc-only changes (use `/doc-feedback` instead)
- For UI-only reviews (use `/mobile-review` or `/customer-facing` instead)

## When TO Use This (MANDATORY)

- After EVERY feature implementation session
- After EVERY `/code-feedback` session that changes logic
- Before EVERY testing session
- Before EVERY `/final-review` session
