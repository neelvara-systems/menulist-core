# Content Layers — Website + Help Docs + Firebase Costs + Changelog

## Purpose

Every feature needs content that goes BEYOND internal docs. These four content layers ensure MenuList's public presence, customer self-service, cost control, and product transparency are maintained alongside every feature.

**Why this matters for a solo founder:**

- `_website.md` → Customers discover your feature (acquisition)
- `_helpdoc.md` → Customers help themselves (reduces support tickets)
- `_firebase.md` → You control costs and know EXACTLY what every feature costs to run (revenue/profit)
- `changelog.md` → Customers trust the product is improving (retention)

---

## Layer 1: Website Content (`_website.md`)

**Audience:** Potential customers visiting menulist.ai
**Tone:** Outcome-focused, benefit-driven, calm confidence. NO hype.
**Language:** MUST follow `__docs__/constitution/02-language-governance.md`
**Location:** `__docs__/[feature-name]/[feature-name]_website.md`

```markdown
## Approved Language (from Constitution)

- [Feature-specific approved phrases]

```

### Writing Rules for Website Content

1. **Benefits over features** — "Your menu updates itself" NOT "Automatic menu synchronization"
2. **Customer language** — Write like the owner (Indian SMB) would describe the problem to a friend
3. **No hype** — Calm confidence. MenuList doesn't need to shout.
4. **Mobile-first copy** — Short sentences. Scannable. Works on phone screens.
5. **One CTA per section** — Don't overwhelm. One clear action.
6. **Social proof > claims** — Show, don't tell. Numbers and quotes beat adjectives.

### Writing Rules for Help Docs

1. **Step-by-step** — Number every step. One action per step.
2. **Screenshot slots** — Mark where screenshots are needed (even if not taken yet)
3. **Plain language** — "Click the blue button" not "Invoke the primary action handler"
4. **Assume zero tech knowledge** — The owner runs a restaurant, not a tech company
5. **Troubleshooting first** — Start FAQ with the most common problems
6. **Escape hatch** — Always provide a way to get human help if self-service fails
7. **Short paragraphs** — Max 3 lines. Mobile-friendly reading.
8. **India-aware** — Consider WhatsApp as primary support channel, regional language hints

## Layer 3: Changelog (`changelog.md`)

**Audience:** Existing customers + potential customers evaluating the product
**Tone:** Calm, factual, confident. Shows the product is alive and improving.
**Language:** MUST follow Language Governance — no hype, no "exciting updates!"
**Location:** `__docs__/changelog.md` (project-level, NOT per-feature)

### Template Structure

```markdown
# MenuList — Changelog

> What's new, improved, and fixed. Updated with every release.

---

## [Date — e.g., February 7, 2026]

### New

- **[Feature Name]** — [1-2 sentence user-facing description of what they can now do]

### Improved

- **[Feature/Area]** — [What got better and why it matters to the owner]

### Fixed

- **[Issue]** — [What was wrong and that it's now resolved. No blame, no drama.]

---

## [Previous Date]

...
```

### Writing Rules for Changelog

1. **User-facing language** — "Your menu now loads 2x faster" NOT "Optimized SSR hydration pipeline"
2. **Calm tone** — No "🎉 Exciting update!" or "We're thrilled to announce". Just state what changed.
3. **Group by impact** — New → Improved → Fixed (most exciting to least)
4. **One line per change** — Scannable. Owners are busy.
5. **Link to help docs** — If a new feature has a `_helpdoc.md`, link to it
6. **Consistent format** — Same structure every release. Predictable = trustworthy.
7. **Constitution alignment** — "Handled automatically" not "AI-powered optimization"

## Layer 4: Firebase Cost Tracking (`_firebase.md`)

**Audience:** Founder, developers, cost auditors
**Tone:** Precise, quantified, actionable. Every operation must have a cost.
**Purpose:** Track EVERY Firestore read/write/delete, Storage operation, and Cloud Function invocation per feature. This DIRECTLY impacts revenue and profit.
**Location:** `__docs__/[feature-name]/[feature-name]_firebase.md`

### Why This Is Critical

- Firebase bills per operation — untracked reads/writes silently drain revenue
- A single bad query in a loop can cost more than the feature earns
- Without this doc, cost surprises are inevitable
- This is the ONLY way to forecast monthly costs per feature
- During 3-year architecture freeze, these costs are locked in

### Template Structure

```markdown
# [Feature Name] — Firebase Cost Tracking

## Summary

- **Collections Used:** [List all Firestore collections this feature touches]
- **Storage Buckets:** [List any Firebase Storage paths used]
- **Cloud Functions:** [List any Cloud Functions triggered]
- **Estimated Monthly Cost:** [Low/Medium/High + rough $ estimate if possible]

## Firestore Operations

### Reads

| Operation                  | Collection       | Trigger    | Frequency | Docs Read | Indexed? | Notes                  |
| -------------------------- | ---------------- | ---------- | --------- | --------- | -------- | ---------------------- |
| [e.g., Load project list]  | projectsMetadata | Page load  | Per visit | 1-50      | Yes      | Uses `where(tId, sId)` |
| [e.g., Get single project] | projectsData     | User click | On demand | 1         | Yes      | Heavy doc (~50KB)      |

### Writes

| Operation               | Collection       | Trigger   | Frequency | Docs Written | Fields       | Notes                      |
| ----------------------- | ---------------- | --------- | --------- | ------------ | ------------ | -------------------------- |
| [e.g., Save project]    | projectsData     | User save | On demand | 1            | merge update | Uses `requestBodyComposer` |
| [e.g., Update metadata] | projectsMetadata | Auto      | With save | 1            | timestamps   | Lightweight                |

### Deletes

| Operation              | Collection   | Trigger     | Frequency | Docs Deleted | Soft/Hard            | Notes             |
| ---------------------- | ------------ | ----------- | --------- | ------------ | -------------------- | ----------------- |
| [e.g., Remove project] | projectsData | User action | Rare      | 1            | Soft (deleted: true) | Never hard delete |

## Firebase Storage

| Operation                 | Path Pattern                           | Trigger       | Size    | Notes            |
| ------------------------- | -------------------------------------- | ------------- | ------- | ---------------- |
| [e.g., Upload menu image] | `MenuListAi/project/files/{timestamp}` | User upload   | 1-5MB   | JPEG 80% quality |
| [e.g., Generated image]   | `MenuListAi/project/generated/{id}`    | AI generation | 0.5-2MB | WebP format      |

## Cloud Functions (if applicable)

| Function                  | Trigger            | Frequency  | Duration | Memory | Notes            |
| ------------------------- | ------------------ | ---------- | -------- | ------ | ---------------- |
| [e.g., processMenuImages] | Firestore onCreate | Per upload | 30-120s  | 512MB  | Calls Gemini API |

## Security Rules Impact

- [List any Firestore/Storage security rules this feature relies on]
- [Note any custom claims or role checks]

## Cost Optimization Notes

- [Current optimizations: batching, caching, pagination]
- [Potential optimizations: what could reduce costs further]
- [Warnings: expensive patterns to watch for]

## Cost Estimate (per 1000 active users/month)

| Resource          | Operations/month | Unit Cost     | Monthly Cost |
| ----------------- | ---------------- | ------------- | ------------ |
| Firestore Reads   | [estimate]       | $0.06/100K    | $X.XX        |
| Firestore Writes  | [estimate]       | $0.18/100K    | $X.XX        |
| Firestore Deletes | [estimate]       | $0.02/100K    | $X.XX        |
| Storage           | [estimate GB]    | $0.026/GB     | $X.XX        |
| Cloud Functions   | [invocations]    | $0.40/million | $X.XX        |
| **Total**         |                  |               | **$X.XX**    |

## DAL Functions Used

| Function                   | File                           | Line | Operation Type |
| -------------------------- | ------------------------------ | ---- | -------------- |
| [e.g., getProjectsByStore] | src/database/projects/index.ts | 45   | Read (batch)   |
| [e.g., updateProject]      | src/database/projects/index.ts | 120  | Write (merge)  |

## API Routes & Their Firebase Impact

| Route                        | Method | Firebase Ops | Rate Limited? | Notes                                |
| ---------------------------- | ------ | ------------ | ------------- | ------------------------------------ |
| [e.g., /api/image-processor] | POST   | 2R + 1W      | Yes (5/min)   | Reads project, writes extracted data |
```

### Writing Rules for Firebase Docs

1. **EVERY operation counts** — No read/write is too small to document
2. **Trace the full path** — From UI trigger → API route → DAL function → Firestore collection
3. **Include frequency** — "Per page load" vs "per user action" vs "background job" changes cost dramatically
4. **Note batch vs individual** — Batch operations are 67% cheaper; document which pattern is used
5. **Flag expensive patterns** — Loops with reads, unbounded queries, large documents
6. **Include indexes** — Missing indexes cause full collection scans (expensive)
7. **Update on every change** — New API route? New DAL function? Update `_firebase.md` immediately
8. **Cost estimates are mandatory** — Even rough estimates prevent surprises
9. **Security rules count** — Complex security rules add latency and cost
10. **Link to DAL functions** — Every operation must link to its exact DAL function (file:line)

### How They Relate

| Doc             | Who Writes        | Who Reads               | Internal/Public       |
| --------------- | ----------------- | ----------------------- | --------------------- |
| `_spec.md`      | Cascade + Founder | CEO/PM/Investors        | Internal              |
| `_impl.md`      | Cascade + Founder | Developers              | Internal              |
| `_marketing.md` | Cascade + Founder | Sales/Marketing team    | Internal strategy     |
| `_website.md`   | Cascade + Founder | **Potential customers** | **PUBLIC**            |
| `_helpdoc.md`   | Cascade + Founder | **Existing customers**  | **PUBLIC**            |
| `_firebase.md`  | Cascade + Founder | **Founder/Developers**  | **CRITICAL INTERNAL** |
| `changelog.md`  | Cascade + Founder | **All customers**       | **PUBLIC**            |

### Flow: Internal → Public

```
_spec.md (what we're building)
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

```
