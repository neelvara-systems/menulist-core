### Law 4: Shared Data — Copy-Paste As-Is Rule

```
When code uses STATIC DATA (business types, country codes, roles, currencies, etc.)
that exists on BOTH frontend (src/) and backend (functions/src/):

1. PRIMARY SOURCE must be a self-contained file in: src/data/shared/
   - No imports from other project files
   - Pure TypeScript only (no React, Next.js, framework code)
   - All types defined inline within the file

2. BACKEND MIRROR is an EXACT COPY in: functions/src/sharedData/
   - Same filename, same contents — byte-for-byte identical
   - NEVER edit backend copy directly — edit frontend first, then copy

3. UPDATE PROCESS:
   a. Edit the file in src/data/shared/
   b. Copy-paste the ENTIRE file to functions/src/sharedData/ (same filename)
   c. Do NOT cherry-pick changes — always full file replacement
   d. Verify: cd functions && npx tsc --noEmit

4. NEVER hardcode static data inline in functions/ code
   - No inline arrays of business types, country codes, roles, currencies
   - Always import from ../sharedData/

5. Country data lives at src/components/atoms/phoneNumberInput/countryData.ts
   (already self-contained) and is copied to functions/src/sharedData/countryData.ts

See: src/data/shared/README.md and functions/src/sharedData/README.md
```

> **Principle:** Mobile is a CORE DEFAULT surface of MenuList, not a secondary consideration.

> Every feature ships with mobile support built-in — not assessed afterward.
> **STATUS:** PWA end-to-end ACHIEVED (Feb 16, 2026) — full user journey from login to logout works on mobile-only.

```
PARADIGM SHIFT (Feb 15, 2026):
Mobile is NOT "Step 5 assessment after desktop is done."
Mobile is PART OF the feature — built in parallel with desktop.
If a feature passes the 4-gate test, mobile UI is delivered
in the SAME session as desktop UI. Not "later." Not "if time permits."

A feature without its mobile component is INCOMPLETE — same as
a feature without its _firebase.md or its feature flag.

TARGET USER: Non-tech SMB owner using MenuList exclusively from

Every new feature MUST:

10. After implementation: run deep audit — compare mobile screen logic line-by-line against desktop counterpart

MOBILE IMPLEMENTATION CHECKLIST (part of feature completion):
☐ _mobile-support.md created with admission test results
☐ If gates pass: mobile screen(s) built using existing DAL
☐ Data format verified against desktop (field names, value formats, DAL return shapes)
```

### Law 12: Operational Monitoring Checklist (Added Feb 20, 2026)

> **Lesson Learned:** Deep review revealed 7 AI routes missing SAFE_MODE, 4 auth routes with zero rate limiting, 4 Razorpay mutation routes unprotected, payment webhook with no Telegram alerts, and master scheduler failures going unnoticed. These gaps are now fixed, and this law prevents them from recurring.

```
Every new or modified API route / Cloud Function MUST pass this checklist:

1. SAFE_MODE CHECK (AI/expensive routes):
   ☐ Any route that calls OpenAI, Gemini, or other AI APIs MUST have:
     const { checkSafeMode } = await import('@lib/ops/safeMode');
     const safeModeResponse = await checkSafeMode();
     if (safeModeResponse) return safeModeResponse;
   ☐ Place BEFORE rate limiting (save rate limit quota when blocked)
   ☐ Fail-open design — if check fails, operations continue

2. RATE LIMITING (all mutation routes):
   ☐ Auth routes → AUTH_SENSITIVE (5/15min per IP)
   ☐ AI routes → AI_OPERATION or AI_EXPENSIVE
   ☐ Payment creation → PAYMENT_SUBSCRIPTION or PAYMENT_TOPUP
   ☐ Subscription mutations → SUBSCRIPTION_MUTATION (5/hour per user)
   ☐ Publish operations → PUBLISH_OPERATION (5/10min per IP)
   ☐ Public endpoints → use IP-based key
   ☐ Authenticated endpoints → use userId-based key
   ☐ Config lives in: src/lib/rateLimit/configs.ts

3. ALERTING (failure paths):
   ☐ Payment failures → createAlert with severity 'critical' or 'warning'
   ☐ Webhook processing errors → createAlert with severity 'critical'
   ☐ Scheduler failures → sendTelegramAlert (direct, not via createAlert)
   ☐ Frontend API routes → use src/lib/ops/alerts.ts (firebase-admin)
   ☐ Cloud Functions → use functions/src/monitoring/alerts.ts
   ☐ All alerts are non-blocking (wrapped in try/catch)

4. HEALTH VERIFICATION (publish/deploy paths):
   ☐ After any publish → fire verifyMenuPublish (fire-and-forget)
   ☐ Cache-busting query param on verification URL
   ☐ Updates store.health field with OK/WARNING/FAILED
   ☐ Triggers alert on consecutive failures

5. FEATURE FLAG:
   ☐ Every monitoring feature has a flag in src/config/features.ts
   ☐ All flags default to OFF (zero cost when disabled)
   ☐ Flags: ENABLE_COST_PROTECTION, ENABLE_OPS_ALERTS, ENABLE_MENU_HEALTH_MONITOR

KEY FILES:
- Rate limit configs: src/lib/rateLimit/configs.ts
- SAFE_MODE check: src/lib/ops/safeMode.ts
- Frontend alerts: src/lib/ops/alerts.ts
- CF alerts: functions/src/monitoring/alerts.ts
- CF Telegram: functions/src/monitoring/telegramAlert.ts
- Publish verify: functions/src/monitoring/publishVerification.ts
- Feature flags: src/config/features.ts
```

### Law 14: Customer-Facing Responsive Layout (Added March 11, 2026)

> **Lesson Learned:** The client menu was capped at 768px max-width for ALL devices, making desktop visitors see a narrow mobile layout on their 1440px screen. Customer-facing pages are the product's public face — they must look professional on every screen size.

```
Every CUSTOMER-FACING page (client menu, OBP, public pages) MUST:

1. Render correctly on all three device tiers:
   - Mobile (<768px): Single column, vertical scroll, compact cards
   - Tablet (768–1024px): 2-column grid, sticky horizontal category tabs
   - Desktop (≥1024px): Sidebar navigation + 2-3 column grid + hover states

2. Use responsive max-widths:
   - Mobile: 768px
   - Tablet: 960px
   - Desktop: 1200px

3. DeviceFrame separation:
   - Editor preview (fromPage='b2c'): Constrains to simulated device widths
   - Live site (fromPage='main-website'): MUST use 100% width
   - NEVER constrain live customer-facing pages with editor frame logic

4. Entity addressability:
   - Public items MUST have human-readable URLs (slugified names)
   - URL format: /menu/item/{slug}-{shortId}
   - Always support old URL formats alongside new ones

5. No settings bloat:
   - Do NOT add toggles for behavior already controlled by layout choice
   - Every new setting must justify: "Would removing this make it worse?"
   - Non-tech SMB owners want it to work, not knobs to turn

BREAKPOINTS: <768 = mobile, 768-1024 = tablet, ≥1024 = desktop
DETECTION: window.innerWidth with resize listener in ClientMenuRenderer
```

## 🛡️ ANTI-PATTERNS TO AVOID

### ❌ Over-Engineering

```
BAD: Creating new data types when existing ones work
BAD: Adding 8 files when 3 suffice
BAD: Building holiday calendar when simple badge needed

GOOD: Use existing workingHours format
GOOD: Minimal file count
GOOD: Scope to P0, defer P1 features
```

### ❌ Wrong File Locations

```
BAD: StoreStatusBadge in templates/website/clientWebsite/
GOOD: StoreStatusBadge in components/atoms/

RULE: Check impl.md File Structure section FIRST
```

### ❌ Missing Feature Flags

```
BAD: Hardcoded feature always on
GOOD: FEATURE_FLAGS.ENABLE_X && <Component />

RULE: Every feature must be toggleable
```

### ❌ Missing MOL Logging

```
BAD: State changes without audit trail
GOOD: logMOLEvent() for price/hours/availability changes

RULE: Add MOL event type to mol.types.ts if tracking new entity
```

### ❌ Skipping Type Checks

```
BAD: Assume code compiles, submit to user
GOOD: npx tsc --noEmit after each major change

RULE: Type check before claiming "implementation complete"
```

### ❌ Applying Patches Instead of Proper Fixes

```
BAD: Type mismatch? Make fields optional to silence the error
BAD: Duplicate interfaces? Just align them without understanding why
BAD: Fix symptom without investigating root cause

GOOD: Investigate WHY the error exists (architecture issue? design flaw?)
GOOD: Understand the feature/data flow before changing anything
GOOD: Fix the root cause (e.g., remove duplicate, single source of truth)
GOOD: Trace data flow: Where is type defined? Where is it used? Why mismatch?

DETECTION:
- Are you adding "?" to make fields optional just to fix a type error?
- Are you changing a type definition without understanding its consumers?
- Are there duplicate types/interfaces that should be consolidated?
- Is there a "quick fix" that doesn't address the underlying design issue?

RESOLUTION WORKFLOW:
1. STOP before applying any fix
2. SEARCH for all occurrences of the problematic type/interface
3. UNDERSTAND the data flow (where defined → where used → why mismatch)
4. IDENTIFY the root cause (duplication? wrong import? missing field?)
5. FIX at the source (consolidate duplicates, fix import, extend type properly)
6. VERIFY consumers still work after the fix

EXAMPLE (CategoryTimeSlot Duplication):
❌ PATCH: Made extractedData.types.ts fields optional to match project.types.ts
✅ PROPER: Deleted duplicate from project.types.ts, imported from extractedData.types.ts

RULE: Never silence a type error without understanding and fixing its root cause
```

### ❌ Redundant Constants/Types

> **📚 See: `IDE_PROMPTS/7. CODE REFACTORING PATTERNS.md` for detailed patterns**

```
BAD: Same data in multiple files (type + separate lookup table)
BAD: Adding new item requires updating 2+ places
BAD: FEATURE_INFO constant that maps to existing type properties

GOOD: Extend type to include all related fields
GOOD: Single source of truth for feature data
GOOD: Consolidate related constants with their types

DETECTION:
- Do you have "info" or "meta" objects that extend existing types?
- Does adding a new item require changes in multiple files?
- Is there a lookup table that could be fields on the type?

SOLUTION:
1. Extend the type with display/meta fields
2. Update data array with new field values
3. Update consumers to use extended type directly
4. Delete redundant file/constant
```

```
### The 10 Laws of MenuList (Summary)

```

1. Default Authority — MenuList decides by default. Owner action is optional.
2. Silence Is a Feature — No banners, no nudges. Silence = confidence.
3. No Explanations — Never explain WHY a decision was made.
4. Owners Override, Systems Resume — Overrides are temporary only.
5. Public Surfaces Demand Perfection — Show less, not wrong.
6. No Cognitive Load — If it makes owner think, don't ship.
7. No Feature Without Autonomy — Dashboards don't qualify as features.
8. Trust > Engagement — Optimize for zero-intervention days.
9. Humans Do Not Patch Trust — Fix system, not story.
10. Authority Is Fragile — Once broken, nearly impossible to restore.

```

### Feature Rejection Gate (5 Questions - ALL Must Pass)

```

Before proposing any feature, answer these 5 questions:

1. Does it REMOVE a decision? (Not add an option)
2. Would anyone NOTICE if we didn't build it?
3. Does it strengthen the CORE MOMENT (customer decides faster)?
4. Can you explain it in ONE SENTENCE without "and"?
5. Will this still MATTER in 3 years?

Score: 5/5 = Proceed to founder review
Score: 4/5 or below = REJECTED (no appeal)

```

### Product Taste Check (Daily Decisions — UI, Copy, Flows)

```

Before adding ANY UI element, copy change, tooltip, toast, or micro-interaction:

1. Should this exist at all? → "If I don't add this, will anyone suffer?"
2. Does this increase or dilute authority? → "Infrastructure or software?"
3. Does this simplify or add noise? → "Is the screen calmer or busier?"
4. Is this infrastructure-level or feature-level? → "Will the owner think about this?"
5. Is this the right thing at current stage? → "Does this help adoption?"

Quick version: "Does this earn its existence? Is the screen calmer after?"
If any fail → cut it.

See: **docs**/constitution/09-product-taste-doctrine.md for full context.

```

### Communication Worldbuilding (All Copy, Marketing, Messaging)

```

Before writing ANY customer-facing text, apply:

1. WHO is reading? Enter their world — start with what they already believe.
2. WHAT must they feel/do after? Engineer the effect, not the expression.
3. ONE idea only — one dominant belief shift, not a feature list.
4. CONCRETE scenario — micro-story beats statistics every time.
5. IDENTITY close — signal "serious businesses do this", not "try our tool".

Persuasion Sequence: Atomic Truth → Hidden Problem → New Standard → Proof → Identity Close

The One-Line Test:
"Would a busy restaurant owner in Mumbai, reading this on their phone
between lunch rush and dinner prep, immediately understand?"
If no → rewrite.

See: **docs**/constitution/10-communication-worldbuilding-doctrine.md for full framework.


## � POST-IMPLEMENTATION REFACTORING CHECKLIST

> **When to Use:** After feature implementation is complete, before final verification. Use this to clean up code, eliminate redundancy, and improve maintainability.

```
1. Check for redundant constants/types - is the same data in multiple files?
2. Check if adding a new item requires updating 2+ places - if yes, consolidate
3. Look for lookup tables that could be fields on existing types - extend types instead
4. Look for separate files with only 1-3 small exports - consolidate with related files
5. Identify the PRIMARY data structure (usually the type/interface) as single source of truth
6. Extend types to include ALL related fields (display info, icons, descriptions)
7. Store icons as STRING names in data, create ICON_MAP in component layer
8. Update consumers to use extended type directly instead of lookups
9. Delete redundant files after moving their contents
10. Update imports in all dependent files
11. Run type check: `npx tsc --noEmit` to verify nothing broke
12. Update verification.md with what was changed
13. Update README.md version history
14. Add visual previews where helpful (emoji icons, thumbnails)
15. Make important buttons more prominent (danger style for destructive actions)
16. Add "Quick Action" buttons for zero-config operations where applicable
17. Improve toggle clarity with descriptive labels and explanations
18. Collapse advanced options by default to reduce cognitive load
19. Use free tier AI models for development testing when available
20. Document all changes including decision rationale (why this approach)
```
